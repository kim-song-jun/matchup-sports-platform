페이지 하나를 열 때마다 하단·상단·데스크톱 내비게이션 링크들이 같은 라우트를 2~10번씩
중복으로 프리페치하던 것을 고친다.

- **원인**: 공유 앱 셸(`AppChromeInner`, `shell.tsx`)이 뷰포트와 무관하게 `DesktopNav`·
  모바일 topbar·`BottomNav`·`DesktopFooter`를 전부 항상 마운트하고, CSS 미디어 쿼리로만
  화면 폭에 안 맞는 쪽을 숨긴다. 그런데 Next.js의 `<Link>` 자동 프리페치는 이 "CSS로만
  숨김"을 감지하지 못해, 화면에 실제로 보이지 않는 링크도 그대로 프리페치를 쏜다. 그
  결과 `/home`·`/tournaments`·`/my`·`/notifications`·`/search`·`/team-matches`·`/teams`
  같은 공용 라우트는 셸 안에서만 2~3곳(데스크톱 탭 + 데스크톱 브랜드 로고/아바타 +
  모바일 topbar 단축 아이콘 + 모바일 하단 탭)이 각각 따로 프리페치했고, 데스크톱 푸터의
  약관·공지 링크 6개도 페이지마다 함께 프리페치됐다. 알파 실측(2026-09-18): 대회 상세
  페이지 방문 1회에 중복 프리페치 35건, 홈 화면 방문 1회에 69건 — 느린 네트워크에서는
  이게 실제 콘텐츠 요청과 대역폭·연결을 다퉈 체감 버퍼링으로 이어질 수 있다.
- **수정**: `DesktopNav`가 이미 5개 탭 + 검색 + 알림 + 마이 아바타 라우트를 전부
  프리페치하므로, 이와 겹치는 자리(모바일 topbar의 홈 단축 아이콘·검색·알림 벨,
  `BottomNav`의 탭 5개, `DesktopNav` 자신의 브랜드 로고 링크)에는 `prefetch={false}`를
  줘서 중복 프리페치를 껐다. `DesktopFooter`의 약관·공지 6개 링크도 클릭 빈도가 낮은
  유틸리티 페이지라 같은 이유로 껐다. Next.js 라우터 캐시는 URL 기준으로 공유되므로,
  어느 자리에서 미리 받았든 다른 자리를 클릭해도 그대로 재사용돼 — 실제 내비게이션
  체감 속도(클릭 시 즉시 전환)는 그대로 유지되고, 중복 네트워크 요청만 줄어든다.
  `NotificationBellLink`(`notification-bell.tsx`)에 `prefetch` prop을 추가해 호출부에서
  선택적으로 끌 수 있게 했다.
- **범위**: 셸(내비·푸터) 레벨의 중복만 다룬다. 개별 페이지 안의 다른 프리페치 패턴
  (예: 대회 상세 페이지의 하위 탭·팀 링크가 각각 1~2회 프리페치되는 것)은 이번
  변경으로 줄지 않는다 — 별도 확인이 필요하다.
