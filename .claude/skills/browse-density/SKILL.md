# 훑는 화면의 밀도

## 개요

목록은 **읽는 화면이 아니라 고르는 화면**이다. 사용자는 카드 하나를 감상하지 않고 여러 개를 견주어 하나를 고른다. 그래서 랜딩의 규칙(큰 그래픽·과감한 여백)을 목록에 그대로 가져오면 **한 화면에 비교할 대상이 부족해져** 오히려 결정이 느려진다.

이 스킬은 `landing-rhythm` 의 반대편이다. 어느 쪽인지 먼저 정하고 시작한다.

| | 읽는 화면 (`landing-rhythm`) | 훑는 화면 (이 스킬) |
|---|---|---|
| 목적 | 이해시키기 | 비교시키기 |
| 스크롤 | 길어도 된다 | 짧을수록 좋다 |
| 그래픽 | 크게, 흐름 안 중앙 | 결정에 기여하는 만큼만 |
| 성공 신호 | 끝까지 읽는다 | 한 화면에서 고른다 |

## 다섯 가지 기준

1. **한 화면에 4장 이상.** 390×844 기준 카드 높이는 **200px 이하**가 목표다. 이보다 크면 화면당 3장 이하가 되어 "비교"가 성립하지 않는다. 실측 기준선은 `references/measure.md`.

2. **미디어 크기는 결정 기여도에 비례한다.** 사진이 *그 자체로 상품*이면(신발·의류·구장 사진) 카드의 절반을 줘도 된다. 사진이 *분위기*면(종목 그래픽, 스톡 이미지) 96px 이하 썸네일이거나 아예 없어야 한다.
   - 판정법: 그 미디어를 지웠을 때 **고르는 판단이 달라지는가**. 안 달라지면 장식이다.

3. **결정 정보가 미디어보다 먼저 온다.** 카드에서 사용자가 실제로 비교하는 값(시간·장소·인원·가격·상태)은 스크롤 없이 보여야 한다. 미디어가 그 값을 아래로 밀어내면 미디어를 줄인다.

4. **필터가 목록을 가리지 않는다.** 필터를 펼쳤을 때 결과가 한 줄도 안 보이면 잘못된 것이다. 좁은 폭에서는 시트·모달로, 넓은 폭에서는 좌측 레일로 분리한다. 적용 버튼은 스크롤과 무관하게 항상 닿아야 한다(시트 하단 고정).

5. **개수를 먼저 말한다.** 목록 상단에 결과 개수와 적용된 필터를 보여준다. 사용자가 "더 좁혀야 하나"를 그 자리에서 판단한다.

## 절차

1. 이 화면이 훑는 화면인지 확인한다. 상세·랜딩·빈 상태면 이 스킬이 아니다.
2. 카드에서 **비교 축**을 3~5개 고른다. 그 외는 상세로 미룬다.
3. 미디어를 기준 2로 판정한다. 장식이면 썸네일로 줄이거나 뺀다.
4. 390 폭에서 카드 높이를 재고 화면당 장수를 계산한다. 4장 미만이면 줄일 곳을 찾는다.
5. UI 착수 규칙(CLAUDE.md): 코드 전에 A·B·C 3안 + 추천안. 축은 "밀도 / 정보량 / 기존 패턴 유지"처럼 갈라야 한다.
6. 구현 후 alpha 배포본에서 390 캡처 + **카드 높이·화면당 장수를 computed 값으로** 잰다. 육안으로 "촘촘해 보인다"는 근거가 아니다.

## 흔한 실수

| 실수 | 왜 문제인가 | 고치는 법 |
|---|---|---|
| 랜딩 규칙을 목록에 적용 | 여백·그래픽이 커져 화면당 장수가 절반이 된다 | 이 스킬의 기준 1·2로 다시 잰다 |
| 장식 그래픽에 카드 절반을 줌 | 비교 축이 화면 밖으로 밀린다 | 96px 썸네일 또는 제거 |
| 배지·칩을 미디어 위에 겹침 | 미디어도 배지도 안 읽힌다 | 배지를 텍스트 블록으로 내린다 |
| 카드마다 주 버튼(`tm-btn-primary`) | 위계가 사라지고 카드가 길어진다 | 카드 전체를 링크로, 버튼은 상세에서 |
| 필터를 목록 위에 아코디언으로 쌓음 | 펼치면 결과가 안 보인다 | 좁은 폭은 시트, 넓은 폭은 좌측 레일 |
