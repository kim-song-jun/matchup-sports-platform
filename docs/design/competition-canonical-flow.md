## 1. 구조 — 대회 아래에 정규 대회와 정규 리그

```
대회 (V1Tournament)
├── 정규 대회   kind='tournament'      format: 토너먼트 · 조별+결선 · 리그 방식 …
└── 정규 리그   kind='regular_league'  시즌 · 티어 · 승강이 붙은 상시 리그
```

- 둘 다 **같은 테이블, 같은 생성 화면, 같은 참가 신청, 같은 경기 운영, 같은 결과 확정**을 쓴다.
- "리그 방식 대회"(`format='league'`)는 정규 대회의 진행 방식 하나일 뿐이다. 정규 리그와 **같은 것**이 아니라
  같은 엔진을 쓰는 다른 `kind` 다. 명칭은 유지한다: **정규 리그 / 리그 방식 대회**(2026-08-23).
- `V1League` · `V1LeagueTeam` 은 사라진다(contract, Task 164). 리그 전용 서비스는 남되 `V1Tournament` 만 읽고 쓴다.

## 2. 매치 — 모든 경기는 팀 대 팀

- **모든 경기는 팀 매치(`V1TeamMatch`)** 다. 대회를 통하면 **공식경기**, 통하지 않으면 **친선경기**.
- 결과는 **팀 전적과 개인 기록 양쪽**에 남는다.
- 대회 대진(`V1TournamentFixture`)을 팀 매치로 옮기는 것은 Phase 3 이다. 그때까지 경기 운영 모듈은
  게임의 출처를 fixture / teamMatch 둘 다로 해석한다(Task 165 BE-1). **새로 만드는 경로는 팀 매치로만 만든다.**

## 3. 참가 — 신청제, 명단은 등번호와 이름

| 단계 | 정규 대회 | 정규 리그 |
|---|---|---|
| 참가 | 팀장 신청 → 운영자 확정 | 운영자 직접 등록·승강 승계팀 자동 등록 + 팀장 신청 → 운영자 확정. 신청을 여닫는 규칙은 대회와 같다(접수 중일 때만, 2026-10-27). 참가팀 정원은 별도 `maxTeams`이며 null/미설정은 무제한이다. 설정한 정원이 차면 접수·직접 등록·확정을 거절하고, 운영자는 설정에서 정원을 늘리거나 해제한 뒤 다시 처리한다. 기존 `maxPlayers`는 팀당 선수 정원을 유지한다(MD-QA #145). |
| 명단 | 신청 시 **등번호 + 이름(닉네임)** 으로 등록 | 같음. 시즌 시작 시각까지 미제출이면 **자격 가드(실명·생년월일·휴대폰·성별부·정원)를 통과한 현재 멤버 전원**으로 자동 확정(`rosterAutoConfirmedAt`). 통과 멤버 0명이면 명단을 만들지 않고 운영자·팀장에게 알린다(Task 164 BE-4b, 구현 PR #1003 — 머지 전까지는 예정 계약) |
| 명단 공개 | 등번호·이름 | 같음 |

- **경기 명단 = 출전자.** 경기 명단(`V1GameParticipant`)에 있으면 그 경기에 뛴 것이다. 선발/후보 구분은 없다.
- **참가 명단이 경기 명단의 기본값이고, 팀이 경기마다 조정한다**(2026-09-28, Task 179). 대회·리그 공통:
  - 경기 명단 = 참가 명단 − 이 경기에서 뺀 사람 − 결장 기간(팀이 등록, 경기 시작 시각 기준) − 출전정지(규정을 넣은 대회·리그만). 뺀 것은 되돌릴 수 있다.
  - 고치는 곳: 경기 상세, 팀 상세 "다가오는 경기", 팀의 선수 × 경기 화면, 결장 기간 등록, 어드민(참가 신청·운영 보드). 모두 같은 기록이다.
  - 조정은 팀 owner·manager(와 운영자)가 **경기 시작 전(`SCHEDULED`)까지**만 한다. 리그도 같다(경기 중 명단 저장 없음). 시작 후 선수 변동은 운영진이 결과 정정으로 반영한다. 단, 플랫폼 어드민(owner·ops)은 종료된 경기의 경기별 명단에서도 빠짐·되돌리기를 저장할 수 있다(2026-10-24). 공식 결과는 이력을 보존한 새 리비전으로 반영하고, 팀장·스태프·support의 마감은 그대로다. **시작 후 팀 교체는 예외다**(2026-10-09) — 공식 결과가 없으면(제출됐지만 확정 전인 결과는 폐기하고) 어드민이 "대진표 수정"으로 팀을 바꾸고, 바뀐 쪽 경기 명단은 새 팀의 참가 명단으로 다시 계산된다(§4).
  - 조정은 한 번에 한 줄씩 기록(`V1GameRosterAdjustment`)으로 남고 지우지 않는다 — 누가·언제·왜.
    조정하지 않은 결과("안 뛴 사람이 뛴 것으로 남음")는 팀 책임이다.
  - 조정은 **선택**이다. 아무것도 안 하면 참가 명단 전원이 출전한다(2026-09-02 동작과 같다).
  - 참가 명단 밖 선수는 경기에만 넣을 수 없다. 참가 명단에 먼저 추가한다.
  - 친선 팀매치는 여기에 해당하지 않는다(참석명단 제출, Task 106).
- **라인업을 따로 정하지 않은 경기의 기본 명단 — 종류별 기준과 검수**(2026-11-08, MD-QA #146 · 사용자 선택 A: 현행 유지 + 기준 명문화):

  | 경기 | 기본 명단 | 자격 기준 |
  |---|---|---|
  | 정규 대회 | 확정된 참가 신청의 활성 선수 | 마감일·어드민 명단 잠금 전까지 팀이 고친 참가 명단 그대로(신청 때 정한 명단으로 고정되지 않는다). 팀원 전체로 덮어쓰지 않는다 |
  | 정규 리그 | 확정된 참가 신청의 활성 선수. 등록 행이 한 번도 없는 팀만 자격 가드(실명·생년월일·휴대폰·성별부·정원)를 통과한 멤버 전원으로 채운다(시즌 시작 시각 크론·대진 생성이 채우고, 채워지기 전 읽기만 활성 팀원 전원으로 보여 준다. 통과 멤버가 0명이면 명단을 만들지 않아 이 폴백이 계속 보인다) | 등록 선수를 전원 뺀 팀은 빈 명단이다 — 팀원으로 다시 채우지 않는다 |
  | 친선 팀매치 | 활성 팀·활성 계정의 활성 팀원 전원. 첫 기록 때 그 UUID로 고정한다(PR #1938) | 자격 가드는 걸지 않는다 — 참석명단 제출 방식이라 원래 느슨하다 |

  - 같은 팀이라도 경기 종류에 따라 기본 명단의 자격 기준이 다른 것은 **의도**다. 통일(자격 가드를 친선·읽기 폴백까지 적용)은 실제 운영에서 자격 미달 선수가 기록에 섞인 사례가 확인되면 따로 결정한다.
  - **대회·리그의 경기별 출전 명단에는 팀이 제출하거나 어드민이 검수·잠그는 단계가 없다.** 현장 도착 검인(선수별 토글·전원 도착, 팀 owner·manager·운영진)은 있지만 출전 여부를 정하지 않는 도착 기록이고, 명단을 잠그지도 않는다. 팀이 하는 일은 경기 시작 전까지 선수를 빼거나 되돌리는 조정뿐이고(선택), 공식 확인은 결과 제출 뒤 어드민이 하는 한 단계뿐이다(§4). 참가 명단은 별개다 — 참가 명단에는 명단 마감일과 어드민 명단 잠금·해제(`roster-lock`)가 있고, 마감·잠금 뒤에는 팀이 참가 명단을 고칠 수 없다(어드민은 풀 수 있다). 대회·리그 경기 전날 양 팀 owner·manager에게 '명단 확인' 알림이 1회 간다(Task 179 R1). 친선 팀매치는 참석명단 저장·제출·정정 요청이 따로 있고(Task 106), 미제출이면 참석명단 알림이 간다. 다만 친선의 제출도 어드민 검수·확인 잠금은 아니다. 경기 단위로 검수 기록·확인 뒤 수정 잠금이 필요해지면 경기 명단에 새 상태가 생기는 큰 변경이므로 현장 분쟁·정정 빈도를 확인한 뒤 따로 결정한다.
  - 검수는 신원 부정행위 판정이 아니다. 명단 기준은 출전 기록의 정확성이고 신원 확인은 별도 흐름(기록 연결)이다.
- **선발/후보 구분은 없다.** 후보 개념(`position='BENCH'` 센티널)은 제거한다. `started` 라는 이름의 컬럼은 **세 테이블**에 있고
  기본값이 서로 다르므로 처분을 따로 적는다(2026-09-02 실측):

  | 컬럼 | 기본값 | 처분 |
  |---|---|---|
  | `V1GameParticipant.started` (라인업·kickoff·교체 엔진) | `true` | **컬럼은 남기고 값을 `true` 로 고정.** 읽는 자리는 손대지 않는다. 마이그레이션은 `position='BENCH'` → `started=true, position=NULL` |
  | `V1GameResultParticipant.started` (결과 리비전 = 공식 기록) | `false` | 출전한 사람은 전부 `true` 로 쓴다(명단 = 출전자). 어드민 결과 정정 화면의 **선발 체크박스는 제거**한다 |
  | `V1TeamLineupPresetEntry` · `V1TeamTacticsBoardEntry.started` | `true` | 팀 내부 도구. 건드리지 않는다 |

  개인 기록의 "선발 N경기" 통계는 출전 수와 같아지므로 **표시하지 않는다**(§6 "잃는 것").
- **교체 추적은 종목 설정으로 갈린다.** 대회 설정 `lineup.substitutions` 가 `'rolling'` 이면 교체를 기록하지 않는다
  (콘솔의 교체 커맨드 없음, 명단에서 바로 득점자 등을 고른다). `'limited'`(11인 축구 등 횟수 제한 종목)면 교체 커맨드와
  `maxSubstitutions` 검증을 유지한다. 그러므로 **대회 설정의 "교체 방식·허용 횟수" 입력과 교체 엔진은 삭제하지 않는다** —
  설정값이 곧 "교체를 기록하느냐" 의 스위치가 된다. 이미 pin 된 대회 설정의 값도 그대로 유효하다.
- **전술보드는 팀 내부 도구다.** 팀이 자기 선발·포지션·좌표를 그리는 용도로만 남고, 대회·kickoff·결과와 **연결이 없다.**
  kickoff 이 전술보드를 읽는 코드는 만들지 않는다(Task 163 BE-2 폐기).

## 4. 경기 진행과 결과 — 확인 한 단계

```
운영팀 실시간 입력  →  사용자 화면 실시간 표시  →  경기 종료(= 결과 제출)  →  어드민 확인  →  확정
      (라이브 콘솔)         (라이브 스코어)                        SUBMITTED         OFFICIAL
                                                                 "확정 전" 태그        태그 사라짐
                                                                                   순위·전적 반영
```

- **이 흐름의 주체 세 축.** 결과를 보내는 쪽은 **운영팀**(대회 스태프 배정 또는 `platform_ops`)이고,
  확인하는 쪽은 **어드민**(정규 대회의 배정 디렉터도 확인할 수 있고, 정규 리그 디렉터는 어드민이 `DIRECTOR_OFFICIALIZE` 스위치를 켠 경우에만 — §6 "정규 리그 결과 확정 주체")이며, **참가팀**(owner·manager 포함)은 명단·채팅·열람만 한다. "운영팀 실시간 입력" 의
  운영팀은 *경기를 운영하는 사람*이지 *경기를 뛰는 팀*이 아니다 — 참가팀이 결과 리비전을 만들거나 승인하는
  경로는 없고 서버가 403 으로 막는다(`GamesService#resolveActor` 의 `regularLeagueResultAction`).
  열람은 참가팀의 **활성 멤버 전원**에게 열려 있다(역할을 가리지 않는다).
  참가팀 활성 멤버는 **자기 팀 경기의 현장 담당자가 될 수 없다**(2026-11-02) — 경기 지정 배정은 거절하고, 필드 단위
  배정이나 배정 뒤 입단으로 겹치면 그 경기만 콘솔·담당 경기 목록에서 빠진다(`tournaments/staff/own-team-fixture.ts`).
- 리그도 대회와 **같은 경기 운영 콘솔**을 쓴다(Task 165). 리그 전용 결과 입력 모달은 없어진다.
- 결과 리비전 상태는 `DRAFT → SUBMITTED → OFFICIAL` 이 행복 경로다. 어드민은 SUBMITTED 를 보고 **확인** 하나만 누른다.
  틀렸으면 그 카드에서 **"고치고 확인"**(운영자·어드민만 SUBMITTED 를 직접 재작성 → 새 SUBMITTED → 확인) 한다 —
  사용자 선택 A안(2026-09-03). `VOID` 는 어드민이 결과를 없던 것으로 할 때만.
  세 중간 상태의 처분(Task 166 실측, 2026-09-03): **`SUPPLEMENT_REQUESTED` · `REJECTED` 는 폐기**(팀에게 되돌려 보내는 왕복 —
  사용자가 없앤 것이 정확히 이 둘. contract PR 에서 기존 행을 `CHANGE_REQUESTED` 로 변환한 뒤 enum 값 제거).
  **`CHANGE_REQUESTED` 는 유지** — 이름과 달리 "팀 왕복" 이 아니라 *운영자 재작성 허용 상태*(데이터 복구 장치)다.
  이것을 지우면 제출된 결과를 다시 쓸 방법이 사라져 시즌 승강이 막힌 실사고가 있다.
- 공개 점수 상태(`PublicScoreStatus`)는 `unavailable | live | official | pending` — SUBMITTED 는 `pending`(점수 + "확정 전").
  단 대회 설정의 가시성 `official_only` 에서는 `pending` 을 내보내지 않는다(운영자가 고른 정책을 이 흐름이 뒤집지 않는다).
- **순위·승점·전적은 OFFICIAL 만 센다.** SUBMITTED 는 사용자 화면에 점수와 "확정 전" 태그로 보이되 순위엔 들어가지 않는다.
- **팀의 이의 제기 경로는 없다.** 확정 뒤 문제는 운영자에게 알려 운영자가 정정한다. 이의 테이블·화면·알림 5종은 제거한다(Task 166 실측: 5종).
  **어드민(플랫폼 운영자)은 언제든 고친다**(2026-10-01) — 정정은 덮어쓰지 않고 새 공식 리비전으로 남고, 양 팀이 확인한 친선 공동 기록도 같다.
- **시작된 경기의 팀 교체**(2026-10-09, 대회 대진 — 토너먼트·대회 내 리그 방식). 어드민이 "대진표 수정"에서 이미 시작된 경기의 팀도 바꾼다.
  - **공식 결과가 없으면 바로 교체**한다(진행 중·일시정지·종료됐지만 결과 없음·결과가 무효로 돌려진 경기·결과가 제출됐지만 확정 전인 경기). 사유가 필수이고 확인 창을 거친다.
    바뀐 쪽의 경기 명단은 새 팀 참가 명단으로 바뀌고, **옛 팀 쪽 기록(득점·카드·반칙·교체·취소 이벤트)은 지워진다.**
    상대 팀 기록은 남는다. 지워진 이벤트가 상대 점수를 만들었다면(옛 팀 선수의 자책골) 그 점수도 같이 사라진다 — 점수는 남은 이벤트로 다시 센다.
    경기 상태·피리어드·시계는 그대로이고, 운영 콘솔은 경기 버전이 올라가므로 옛 화면의 명령은 거부된다(`VERSION_CONFLICT`).
  - **공식 결과가 있으면 교체하지 않는다**(409 `FIXTURE_RESULT_MUST_BE_VOIDED`). 어드민이 결과를 먼저 무효(`VOID`)로 돌린 뒤 교체하고 결과는 다시 입력한다 — 자동 무효화는 없다.
    제출됐지만 확정 전인 결과(`DRAFT`·`SUBMITTED`·`CHANGE_REQUESTED`)는 교체 트랜잭션이 사유와 함께 `VOID` 로 폐기하고(공식 결과로 집계되지 않음), 경기는 "유효한 공식 결과 없음" 상태가 되어 새 팀 기준으로 결과를 정정 흐름(`VOID_REENTRY`)으로 다시 입력한다. 취소된 경기는 막는다.
  - 진출 연결·자리(slot)에 묶인 쪽은 그대로 직접 못 바꾼다(`BRACKET_SOURCE_SLOT_LINKED`·`SLOT_LINKED`·`SLOT_LOCKED`). 정규 리그(`kind=regular_league`)의 사이드 배정 가드는 이 결정의 범위 밖이다.
  - 감사 로그(`tournament.bracket.fixture.started_team_change`)에 사유·지운 이벤트 수·교체 전후 점수·폐기한 결과 리비전(id·상태)이 남는다.
- 피리어드(전후반)는 대회 기본 `periods` 배열로 정하고, 정규 대회는 조별·각 결선 단계별 재정의와 조별리그 조 하나의 재정의를, 대회·리그는 시작 전 경기 하나의 재정의를 선택적으로 둔다. 우선순위는 경기 > 조 > 단계 > 대회 기본값이고, 재정의가 없으면 바로 위 설정을 상속한다. 어느 재정의를 저장해도 대회 기본 설정은 바뀌지 않는다. 새 경기는 생성 시점의 조·단계 설정 버전을 고정하고, 설정 변경은 그 설정을 따르는 시작 전 경기만 옮긴다. 이미 시작했거나 끝난 경기는 만든 때의 설정을 유지한다. 어드민은 생성 시와 생성 후 정보 화면에서 기본값·단계 재정의를, 대진 화면에서 조·경기 재정의를 바꿀 수 있어야 한다(Task 165, Task 20261029).

- **정규대회의 조별+결선은 한 대회 안에서 상위·하위 결선을 함께 운영할 수 있다**(2026-10-12 사용자 확정, Task 20261057 확장). 조별 1·2위는 상위, 3·4위는 하위로 진출한다. 신청·명단은 한 번 관리하고 결승 결과와 우승·준우승은 결선별로 표시한다. 팀 시상 안내는 대회 전체 또는 상위·하위별로, 개인상은 항목마다 전체·상위·하위를 어드민이 조절한다. 정규 리그는 이 확장의 대상이 아니다.

## 5. 전적과 기록

- **팀 전적** 탭: **전체 / 대회 / 리그 / 친선**. 공식경기는 대회·리그로, 친선경기는 친선으로 들어간다.
- **개인 기록**에도 같은 구분이 들어간다. 서버는 팀 전적과 **같은 분류 함수**(`team-record-category.ts`)로 `type`
  (`tournament | league | friendly`)을 싣는다 — 이미 구현됨(2026-09-03 실측). `matchType` 은 구 클라이언트 별칭이라 리그를 가르지
  못하며 소비처 0 → 다음 정리 스윕에서 삭제. 화면(개인 기록 4탭)은 Task 166 FE — 사용자 선택 A안(팀 전적과 같은 탭, 2026-09-03).
- 출전 수는 경기 명단 행 존재로 센다(경기 명단 = 출전자). 골·도움 0 인 출전도 기록에 남는다. 선수 카드의 능력치(3경기)·등급(15·30경기)이 이 수로 열리므로, §3 의 경기별 조정이 곧 카드 정확도다.
- **몰수 경기에서도 기권 전 실제 개인 기록(골·어시스트·카드)은 남기고**, 화면에는 몰수 경기의 기록이라는 표시를 한다(2026-11-09, §6 결정 이력).
- **동점 처리 순서는 종류별로 다르다.**
  - **정규 리그**는 플랫폼 공통이고 대회별 설정이 없다 — 승점 → 골득실 → 다득점 → 상대전적 → 최소 실점.
    (5번째는 2026-09-17 추가 — 아래 결정 이력 참조. 화면은 상대전적을 '승자승'으로 표기한다.)
    예전 `V1League.tieBreakJson` 은 생성 시 이 값이 박히고 바꾸는 경로가 아예 없어(운영자 화면·API 모두)
    사실상 상수였다 — 통합 축으로 옮기면서 컬럼을 따라 옮기지 않고 `league-tie-break.ts` 한 곳으로 모았다
    (2026-09-03, Task 164 BE-5).
  - **정규 대회의 조별 순위는 대회마다 고른다**(2026-11-07 사용자 선택) — 승점은 언제나 처음, 시드 추첨은 언제나 마지막이고,
    그 사이의 맞대결·득실차·다득점·페어플레이를 어드민이 대회 생성 화면과 정보 수정 화면에서 순서대로 놓는다.
    기본값은 승점 → 맞대결 → 득실차 → 다득점 → 페어플레이 → 추첨(이 순서를 바꾼 적 없는 대회는 순위가 그대로다).
    맞대결은 앞 기준으로 이미 갈린 팀을 빼고 아직 같은 팀들끼리의 경기만 센다 — 승점 바로 다음이면 승점이 같은 모든 팀의 맞대결 성적표(승점·득실·득점)이고, 득실차 같은 기준 뒤로 옮기면 그 기준까지 같은 팀들만 비교한다.
    예선 공식 결과가 하나라도 생긴 뒤에는 바꿀 수 없다(`409 TIE_BREAK_ORDER_LOCKED`). 저장 순위·공개 「공동 n위」·어드민 동률
    판정이 모두 이 대회의 순서를 쓴다. 공개 조별 순위표 아래에 그 대회의 순서를 한 줄로 보여 준다.

## 6. 결정 이력 — 무엇이 바뀌었나, 무엇을 얻고 잃나

2026-11-03 사용자 요청: 독립 정규리그를 **독립 리그 → 독립 리그 다음 시즌**으로 잇는다. 어드민이 진행 중이거나 끝난 독립 리그에서 '다음 시즌 만들기'를 누르면 지난 시즌 설정(종목·지역·성별·참가비·계좌·명단 인원·정원·경기 수·경기 시간)을 채운 리그 개설 화면이 열리고, 새 리그가 `previousLeagueId` 로 지난 리그를 가리킨다(지난 리그당 하나). 지난 시즌 확정 팀은 공개 화면의 '다음 시즌 재참가 신청'으로 그 팀이 골라진 신청 화면에 가거나 어드민이 참가팀 관리에서 한 번에 넣고(바로 참가 확정), 어느 쪽이든 행이 한 번도 없던 명단이면 지난 시즌 명단 중 아직 팀의 활성 멤버이고 자격이 되는 선수를 지난 번호 그대로 옮긴다. 다음 시즌 접수를 처음 열면 아직 신청하지 않은 지난 시즌 팀장·매니저에게 한 번 알린다. 리그 체계 전환과는 **둘 중 하나만** 한다 — 다음 시즌을 이은 리그는 전환을, 전환한 리그는 다음 시즌 잇기를 막는다(두 경로가 원본 리그 행을 같은 트랜잭션에서 잠근다). 얻는 것: 리그 신청 화면의 '다른 리그' 안내가 실제 다음 시즌으로 이어지고, 같은 팀이 명단을 다시 꾸리지 않고 재참가한다. 비용: `v1_tournaments.previous_league_id` 컬럼(마이그레이션)이 생기고, 옮긴 명단은 제출 전 팀이 확인해야 하며 지난 시즌 뒤 바뀐 등번호는 팀이 고친다. 리그 체계 안의 리그는 그대로 승강 확정으로 잇는다.

2026-11-03 사용자 승인: 종료된 독립 정규리그의 공식 순위를 배치 성적으로 사용해 새 리그 체계와 첫 시즌의 티어별 리그를 만든다(6팀 예: 상위 3팀 1부, 하위 3팀 2부). 1~3티어, 티어당 최소 2팀이며 확정 참가팀 전원을 한 번씩 배정한다. 원본은 독립 배치 리그로 남기고 경기·순위·선수 기록을 변경·복사하지 않는다. 미리보기 후 결과가 바뀌면 재확인을 요구하고, 자동 배정 변경 및 티어 경계 완전 동률은 사유를 기록한다. 최초 배정과 이후 승강은 별개다. 생성·등록·원본 연결과 배정 감사는 한 Serializable 트랜잭션이며 원본당 한 번만 확정한다. 1티어 체계도 승강 없이 다음 시즌을 생성한다. 연결/지문/배정 내역은 보존 대상인 전환 감사 로그에 남긴다.

2026-11-04 사용자 확정(알파 QA 후속): 리그 체계 전환도 다음 시즌 잇기처럼 **원본 리그의 확정 명단을 첫 시즌 티어로 옮긴다**(같은 `copyPreviousSeasonRoster`, 원본 리그를 출처로 넘긴다 — 티어가 여럿이라 `previousLeagueId` 1:1 연결은 쓰지 않는다). 전환한 원본 리그의 공개 화면은 첫 시즌 티어와 편성 팀(`nextSeasonTiers`)을 받아 보는 사람의 팀이 든 티어로 잇는다. 어드민의 '팀 추가'와 '지난 시즌 팀 넣기'는 이미 신청이 진행 중인 팀(입금 대기 등)을 넣지 않는다(아직 내지 않은 draft·취소한 신청은 그대로 확정으로 올린다) — 넣으면 결제가 '대기'인 채 확정됐다. 그 팀은 신청 관리에서 입금을 확인해 확정한다.

2026-10-29 사용자 요청: 단계 재정의에 더해 조별리그 조 하나와 경기 하나(대회·리그 모두, 시작 전)의 단판·전후반을 따로 바꾼다. 강 단계는 블록이 보통 하나라 단계 설정 한 곳에서만 바꾼다(사용자 선택 안 1). 좁은 설정이 넓은 설정보다 우선하고, 넓은 설정을 바꿔도 따로 정한 조·경기는 따라가지 않는다(사용자 선택). 수정 화면은 위 설정 값을 보여 주되 저장은 그 조·경기에만 한다 — 대회 기본 설정은 절대 바꾸지 않는다. 얻는 것: 특정 조·경기만 단판으로 운영하려고 전체 설정을 건드리는 일이 사라진다. 비용: 조 재정의 열과 경기 재정의 표시가 추가되고, 위 설정 변경이 따라갈 경기를 고르는 범위 계산이 한 단계 늘어난다.

2026-10-28 사용자 요청: 대회 전체에 하나뿐이던 경기 시간을 **기본값 + 단계별 선택 재정의**로 확장한다. 조별 단판 15분과 결승 전·후반 각 10분처럼 운영 전에 함께 저장하고, 생성 후에도 단계별로 수정한다. 재정의가 없는 단계는 기본값을 상속하며, 변경은 해당 단계의 시작 전 경기만 새 immutable 설정 버전으로 옮긴다. 시작·종료 경기는 기존 버전을 유지한다. 얻는 것: 조별 마지막 킥오프 직후 전체 설정을 바꾸는 시간 의존 우회와 남은 조별 경기 오변경 위험이 사라진다. 비용: 단계 설정 행과 기본 규칙 변경 시 재기반 로직이 추가되고, main 승격 전에 DB migration이 필요하다.

2026-10-27 사용자 개발 요청 및 UI A안 선택: 전체 대진 설정을 참가 수 → 조 편성과 진출 → 팀 배정 → 서버 미리보기로 제공한다. 총 4~64팀 짝수, 조별 2~8팀과 서로 다른 진출 수를 지원하며 결선은 홀수도 가능하다. 실제 경기는 합계 240개 이내로 제한한다. 조별 순위 출처는 부전승이어도 유지하고, 수동 조의 미설정 진출 수를 2팀으로 추측하지 않는다. 완료된 조에서 실제 결선에 배정된 팀은 파란 진출 강조에 포함한다. 기존 v1/특수 20팀은 보존한다. 얻는 것: 불균등 조와 다양한 참가 수를 같은 흐름에서 운영하고 수동 진출 표시를 복구한다. 비용: 조별 진출 비율과 같은 조 재대결 가능성을 운영자가 검토해야 하며 새 생성은 테스트 대회 활성화와 alpha 검증을 거쳐 출시한다.

2026-10-27 사용자 확정: **정규 리그 참가 신청을 대회와 같은 방식으로 받는다.** ① 신청은 대회처럼 저장 상태가 `open`(접수 중)이고 마감 전일 때만 받는다 — 판정은 `registration-window.ts` 하나를 대회·리그·목록 SQL·웹이 같이 쓴다. 운영자는 리그 상단의 '접수 시작하기'(초안·마감 → 접수 중, 마감은 정하거나 비운다)와 '접수 마감하기'(접수 중 → 마감)로 여닫는다. ② 리그를 시작하면(`in_progress`) 신청이 닫히고 다시 열 수 없다 — 시즌 중 합류는 운영자 직접 등록이다. 보류 중에도 받지 않는다(MD-QA #183 해소). ③ 리그 상태 이름도 대회처럼 나눈다: 어드민 초안·접수 중·마감·시즌 진행 중·종료·보류, 공개 화면 준비 중·모집 중·마감·시즌 진행 중·종료. ④ 리그 만들기는 대회처럼 단계형(기본 정보 → 참가팀·신청 → 경기 설정 → 확인)이고, 팀 직접 추가는 유지하되 0팀이어도 만든다. 신청 마감·참가비·계좌를 생성 때 같이 정하고, 새 리그(독립 생성·시즌 시드·승계)는 `draft`(초안)로 시작한다. ⑤ 배포 때 시작 전(초안·마감)이면서 마감이 남아 신청을 받던 리그는 `open` 으로, 예전 `open` 인데 마감이 없어 신청을 안 받던 리그는 `closed` 로 옮긴다(보류 리그는 돌아갈 상태를 같은 규칙으로). 이 결정이 대체하는 것: 2026-09-04 "리그 신청의 판정자는 마감 시각 하나"(아래 '리그 신청 마감' 행), 2026-10-07 '지금 마감'이 마감 시각을 당기는 방식('리그 즉시 모집마감' 행), 2026-10-18 "신규 리그는 `closed` 로 생성", 2026-10-19 "리그 상태는 모집완료·진행 중·보류·종료 4개". 얻는 것: 대회와 리그가 신청을 여닫는 말과 버튼이 같아지고, 보류·시작한 리그가 신청을 받는 틈이 사라진다. 잃는 것: 시즌이 시작된 뒤에는 팀이 스스로 신청할 수 없고, 운영자가 접수를 한 번 시작해야 한다(마감만 정해서는 열리지 않는다).

2026-10-24 사용자 요청: 어드민 경기별 명단에서 종료 경기의 빠짐·되돌리기를 허용한다. 기존 결과·라인업은 보존하고 새 결과 리비전과 변경 주체를 남긴다. 경기 점수는 유지하며 득점·카드 등 개인 기록이 있는 선수는 기존 결과 정정에서 함께 수정하도록 저장을 거절한다(기록을 조용히 삭제하지 않는다).

2026-10-18 사용자 확정: 신규 리그(독립 생성·시리즈 새 시즌)는 `closed`(모집 마감)로 생성한다. 대진 생성/재생성·슬롯 팀 배정·결과 확정으로 자동 시작하지 않는다. 운영자가 기존 상태 변경 API로 `active`를 선택하는 **리그 시작하기**를 눌러야 `in_progress`가 되고, 그 전 경기 시작은 `409 LEAGUE_NOT_STARTED`로 거절한다. 기존 행은 상태 백필 없이 `requiresExplicitStart=false` 기본값으로 기존 `draft`/`open`/`closed`의 자동 시작·경기 시작을 유지한다. 신규 생성만 `requiresExplicitStart=true`로 구분한다(2026-10-18 PR 호환성 보강). 신청 열기/마감은 기존 명시적 마감 시각 계약을 유지한다. 얻는 것: 일정 준비와 실제 시작이 분리된다. 잃는 것: 운영자가 시작을 한 번 명시해야 한다. 2026-10-19 최종 사용자 확정: 리그 상태는 **모집완료·진행 중·보류·종료 4개**다. 내부 API `draft`는 호환용으로 유지하고 `draft/open/closed`를 모두 모집완료로 표시한다. 준비 중·모집 중을 별도 수명주기로 두지 않는다. 참가 신청 가능 여부·마감·정원과 공개 여부는 별도 정보다. 신규 생성 시 표시도 모집완료이며 기존 데이터 백필·전이·권한·경기 시작 조건은 바꾸지 않는다. 앞선 5상태 제안은 이 결정으로 대체됐다.

2026-10-21 사용자 확정: 상대 팀 없이 끝난 **일반 팀매치**(친선·플랫폼 주관, 리그·대회 대진 제외)는 자동으로 `cancelled`가 된다. 신청 마감이 지났고 대기 신청이 없으면 그때, 대기 신청이 있으면 경기 시작 시각에 취소하고 행은 지우지 않는다. 1팀이면 그 팀에, 대기 신청 팀에는 1팀·0팀과 상관없이 따로 알리고, 0팀이고 대기 신청도 없으면 알리지 않는다. 배포 전에 끝난(경기 시작이 지났고 24시간 넘은) 매치는 알림 없이 취소만 한다 — 경기 전인 매치는 마감이 오래전이어도 알린다. 얻는 것: 열릴 수 없는 매치가 목록에서 빠지고 팀이 결말을 안다. 잃는 것: 마감 뒤 일정을 바꿔 다시 모집하던 길이 닫힌다(새로 만든다).

2026-10-20 (MD-QA #174): 한 경기에서 한 선수가 **옐로 2장 + 레드**를 받으면(콘솔이 두 번째 옐로 뒤에 레드를 따로 기록한다, MD-QA #81) 레드 한 장마다 옐로 2장은 **레드로 바뀐 경고**로 본다. 카드 저장 모양(`{ yellow, red }`)은 그대로이고 해석만 바꾼다(`classifyGameCards`). 출전정지는 레드 정지 규정이 있으면 그 옐로 2장을 경고 누적에 넣지 않는다(레드 규정이 없으면 그대로 센다). 페어플레이는 옐로 1+1·직접 퇴장 4 = 6점이 아니라 경고 누적 퇴장 3점이다. 옐로 1장 뒤 직접 레드는 둘 다 센다. 얻는 것: 같은 반칙으로 두 번 정지되지 않고(규정 "옐로 1장마다 1경기·레드 1경기"에서 3경기가 1경기로), 뒤 경기 누적에도 남지 않는다. 잃는 것: 정지는 그때그때 계산이라 진행 중인 대회·리그에서 바로 바뀌고, 저장된 순위의 페어플레이 숫자는 순위를 다시 계산해야 바뀐다.

### 2026-11-07 — 대회별 동점 순서

사용자 선택(QC1106 리허설 결정 페이지, C안 — 추천안 A와 다르게 고름): 정규 대회(조별 순위를 쓰는 진행 방식 전부)마다 승점 다음의 동점 순서를 어드민이 고른다. 5절의 "대회별 설정은 없다"는 정규 리그에만 남기고 정규 대회는 번복한다 — 운영자가 외부에 공지한 대회 규정(예: 득실 먼저)과 화면 순위가 어긋나지 않게 하기 위해서다. 후보는 지금 쓰는 맞대결·득실차·다득점·페어플레이이고 승점은 처음, 추첨은 마지막으로 고정이다. 맞대결은 승점 다음이 아닌 칸에 놓이면 앞 기준으로 갈린 팀을 뺀 나머지끼리의 직접 경기로 갈린다(승점 바로 다음이면 승점이 같은 모든 팀의 맞대결 성적표라 기본 순서의 순위는 그대로다). 저장 위치는 공유되는 경기 규정 판(내용 해시로 버전 관리)이 아니라 대회 행의 `tieBreakOrder`(null = 기본 순서)라 다른 대회의 규정 판은 바뀌지 않는다. 예선 공식 결과가 하나라도 생긴 뒤에는 순서 변경을 `409 TIE_BREAK_ORDER_LOCKED` 로 막고(같은 순서를 다시 보내는 저장은 막지 않는다), 순서 변경과 결과 확정이 겹치지 않게 대회 잠금에 더해 이 대회의 경기 행을 잠가 커밋 전인 결과 확정이 끝나길 기다린 뒤 한 번 더 확인한다. 저장 순위 계산(결과 확정 자동 반영·어드민 재계산)·공개 「공동 n위」·조별 진출 판정·N개 토너먼트의 동률 감지·5개 조 12강 배정의 조 간 비교(득실차·다득점만)가 모두 같은 대회 순서를 쓴다: 공개 「공동 n위」와 어드민 동률 판정은 리그 계산기가 아니라 저장 순위 비교기가 추첨 단계까지 가서야 갈린 묶음만 동률로 본다. 얻는 것: 공지한 규정대로 순위가 나오고 공개 표·어드민·배정 화면이 같은 말을 한다. 잃는 것: 대회마다 순서가 달라 같은 팀의 대회 간 순위 비교가 어긋날 수 있고, 맞대결로 갈린 쌍이 리그 계산기 기준 「공동」에서 빠지는 등 일부 대회의 「공동 n위」 표시가 달라진다(저장 순위는 그대로). 정규 리그의 순서는 바뀌지 않는다. 화면: 대회 생성·정보 수정의 「동점일 때 순서」 칸(위로/아래로)과 공개 조별 순위표 아래 한 줄 안내.
