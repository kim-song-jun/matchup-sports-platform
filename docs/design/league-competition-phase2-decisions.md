# 리그·대회 통합 Phase 2 — 사용자 확정 결정 (D7 · D9 · D10)

> **2026-08-29 사용자 확정.** 되묻지 말 것 — 이건 제안이 아니라 결정이다.
>
> **왜 이 파일이 있나**: 이 결정들은 오케스트레이터 세션의 기획서와 결정 아티팩트에만
> 있었다. **아티팩트는 결정을 *받는* 도구지 보관소가 아니다** — 사용자가 지우면 사라지고,
> 세션이 끝나면 기획서도 사라진다. 실제로 같은 날 결정 아티팩트 두 개가 지워졌고 그중
> 하나(과거 알림 `deepLink`)는 저장소 기록이 0건이어서 **다시 물을 뻔했다.**
> → 그 건은 `docs/ops/read-swap-preflight.md` 7절에 있다.
>
> **착수 시점**: Phase 2. **지금 만들지 않는다** — 참가팀 백필 실행과 read-swap 이 선행이다.

## D1~D6 · D11~D13 — 결정문

여기 있는 것은 **결정 자체**다. 3안이 필요한 것은 D7·D10 뿐이고, 나머지는 구현 방향이다.

| # | 결정 | 무엇을 정하나 |
|---|---|---|
| **D1** | **물리 통합 — 한 테이블** | `V1League` 를 대회로 흡수. 대진 표현도 하나로 |
| **D2** | 개인 매치(`V1Match`)는 **별도 도메인 유지** | 모임 성격이라 결과·전적 체계 **밖**에 둔다 |
| **D3** | **대회 단위 명단만** | **명단 = 참가자 = 출전자.** 경기별 출전 확정 단계를 두지 않는다 |
| **D4** | 출전 명단만 공개 | 등번호·이름은 공개, **선발/후보·포지션·좌표는 비공개** |
| **D5** | 리그 명단은 **시즌 시작 시 1회 확정** | 기본값 = 현재 팀 멤버 전원. 중도 추가는 운영자 승인 |
| **D6** | **두 경로 병행, 한 계약** | 스태프 배정 시 라이브 콘솔 / 미배정 시 운영자 사후 입력. **둘 다 즉시 확정 + 이의 7일** |
| **D8** | **전량 백필** | expand → dual-write → backfill → read-swap → contract |
| **D11** | 순위는 **대회 엔진으로 통일** | `tournaments/competition-config/competition-standings.ts` 로 리그 호출부를 재배선 |
| **D12** | 승강 확정 시즌은 **동결** | 진행 중·미확정은 새 규칙으로 재계산, 새 시즌은 새 규칙 |
| **D13** | 리그별 tie-break 설정 **버린다** | 순서는 대회와 같이 **코드 고정**. `tieBreakJson`(`schema.prisma:1877`) 정리 |

### ⚠️ D3 의 대가 — **화면에 바로 나타난다**

> 명단 20명인 팀이 리그 10경기를 치르면 **벤치에만 있던 사람도 10경기 출전으로 집계된다.**
> 선수 카드·개인 전적·팀 기록에서 "출전"이라는 낱말이 사실과 어긋난다.

**절반은 이미 대응됐다** — 라벨을 **"출전 → 엔트리"** 로 바꾼 것이 그 대응이다
(`profile/player-card.ts` 의 `APP: '엔트리'`).

**나머지 절반은 열려 있다.** 현장 체크인(`arrivedAt`, `schema.prisma:3308`)으로 **실제 출전**을
가리는 것은 **이번 범위 밖**이고, 나중에 붙일 수 있도록 **컬럼은 그대로 둔다.**
즉 지금 수치는 "엔트리에 든 횟수"지 "실제로 뛴 횟수"가 아니다 — 그 구분이 필요해지면
`arrivedAt` 이 이미 있다.

### D12 의 "동결"은 **새 기능이 아니다 — 재계산을 돌리지 않는 것이다**

두 축의 현재 모양이 다르다:

| | 지금 |
|---|---|
| 대회 | 순위를 **저장**한다 (`V1TournamentStanding` + `POST /admin/tournaments/:id/standings/recalculate`) |
| 리그 | 저장 모델 없이 **매 호출 계산**한다 |

D11 로 대회 엔진에 수렴하면 리그도 저장형으로 옮겨간다. 그러면 D12 는 이렇게 성립한다:

1. 백필 시점의 **현행 규칙 순위를 그대로 저장** = **그게 곧 스냅샷이다**
2. `V1LeaguePromotion` 행이 있는 리그(= 승강 확정)는 **재계산 대상에서 제외**
3. 나머지만 새 엔진으로 recalculate

> **되돌리기도 재계산 한 번이다.** 동결을 위해 만들 것이 없고, 풀기 위해 지울 것도 없다.

## D7 — 참가 경로: **둘 다 신청제로 통일**

> 리그는 **승강 승계팀 자동 등록 + 빈자리 신청.**

### 무엇이 바뀌나

지금 리그는 **운영자가 팀을 추가**한다(`league-match-admin.service.ts` 의 `addTeam(user, …)`).
이걸 **대회처럼 팀장이 신청하는 흐름**으로 바꾼다.

| | 지금 (리그) | 바뀐 뒤 |
|---|---|---|
| 참가 주체 | 운영자가 추가 | **팀장이 신청** |
| 승강 승계팀 | 운영자가 추가 | **자동 등록** (신청하지 않는다) |
| 남은 자리 | — | **신청을 받는다** |
| 경로 | 어드민 화면 | `/competitions/:id/apply` — **대회와 공유** |

### 3안이 갈릴 축

> **자동 등록 팀과 신청 팀이 한 화면에 어떻게 공존하는가.**

자동 등록된 팀에게는 신청 버튼이 **무의미**하고, 신청하려는 팀에게는 **빈자리 수**가 보여야
판단이 선다. 한 화면이 두 상태의 사용자를 동시에 받는다.

### 후속 D9 — 정원 초과

> **자동 규칙 없음 — 운영자가 보고 직접 조정.**

신청은 받되 **최종 참가팀은 어드민이 정한다.** 선착순·추첨 같은 자동 규칙을 두지 않는다.
**조정 사유 기록은 필수**다.

## D10 — 명단 미제출 팀: **자동 확정 + 경고·알림**

> 시즌 시작 시각에 **현재 멤버 전원으로 자동 확정**하고, 팀 운영진에게
> **사전 리마인더**와 **확정 통보**를 보낸다.

### 무엇을 푸는 문제인가

D5(시즌 명단 확정)를 **안 한 팀**이 명단 없이 시즌에 들어가는 것을 막는다.

1. 시즌 시작 시각에 **현재 멤버 전원**으로 자동 확정
2. **사전 리마인더**(확정 전) + **확정 통보**(확정 후) — 알림 두 개
3. 자동 확정된 것은 **표식**을 남긴다 (직접 확정한 것과 구분돼야 한다)

> ⚠️ **표식 컬럼(`autoConfirmed` 류)은 아직 없다.** 2026-08-31 실측 — `schema.prisma`·
> `apps/v1_api/src`·`apps/v1_web/src` 전부 **0건**이고, 참가팀 백필 PR(#870)에도 스키마
> 변경이 없다. "백필 PR 에 넣기로 했다"는 기억이 있으나 **들어가지 않았다.**
> **D10 착수 시 이 컬럼부터 만든다** — 표식 없이는 3안의 "구분해서 보여준다"가 성립하지 않는다.
>
> **아직 참인지 확인**: `grep -rn 'autoConfirmed' apps/v1_api/prisma/schema.prisma apps/v1_api/src`

### 3안이 갈릴 축

> **① 알림·경고를 어디에 띄우는가** — 팀 상세? 리그 상세? 푸시만?
> **② 자동 확정된 명단임을 화면에서 어떻게 구분하는가** — 직접 확정한 것과 섞이면 안 된다.

### ⚠️ 기획서가 스스로 적은 우려 — **3안 중 하나는 이걸 정면으로 다뤄야 한다**

> *"D10의 자동 확정은 **팀장이 손대지 않은 팀을 예전 상태 그대로 되돌린다**"*
> — 기획서 `:625`. 그리고 **"완화가 해소는 아니다"** 라고도 적혀 있다.

즉 **D5로 얻으려던 것**("팀이 명단을 의식적으로 확정한다")이 D10 때문에 약해진다.
자동 확정은 *명단 없는 팀*은 없애지만 *의식적 확정*은 되살리지 못한다.

**세 안 중 적어도 하나는 이 트레이드오프를 완화가 아니라 설계로 다룬다** —
예컨대 자동 확정 명단에 **기능 제약**을 걸거나, 확정 통보를 **되돌릴 수 있는 행동**으로
만들거나. 나머지 안은 알림·표시 방식만 다르게 가도 된다.
