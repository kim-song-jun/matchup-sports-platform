# Alpha 인증 메일·문자 발송

Alpha는 실제 수신 주소에는 메일과 문자를 발송한다. 예약된 테스트 주소(`.test`, `example.com` 계열, `010-0000-xxxx`)는 외부로 발송하지 않고 권한이 없는 테스트 계정에만 `devCode`를 반환한다. 운영에서 쓰는 문자 발송 계정을 공유하므로 Alpha의 실제 문자 발송도 비용과 발송량에 포함된다.

## 메일 권한

- SES는 `ap-northeast-2`의 검증된 `teameet.co.kr` 도메인을 쓰지만 발신 주소는 `alpha-no-reply@teameet.co.kr`으로 분리한다.
- IAM 사용자 `teameet-alpha-ses`의 `TeameetAlphaSesSend` 인라인 정책은 해당 도메인에 대한 `ses:SendEmail`과 위 발신 주소만 허용한다. 운영 발신 주소 및 다른 AWS 권한은 허용하지 않는다.
- `ALPHA_SES_ACCESS_KEY_ID`와 `ALPHA_SES_SECRET_ACCESS_KEY`는 `/teameet/alpha/env/` 아래 SSM `SecureString`으로 보관한다. Alpha EC2 역할은 해당 두 항목을 읽지만 GitHub 배포 역할은 덮어쓸 수 없다. 워크플로는 호스트에서만 값을 읽어 보호된 런타임 설정에 반영한다. 키 값과 설정 파일은 로그로 출력하지 않는다.
- Alpha API는 전용 키 쌍이 없거나 불완전하면 인스턴스 역할로 전환하지 않고 메일 발송을 비활성화한다. 운영 API는 기존 인스턴스 역할을 계속 사용한다.
- 최초 생성은 `scripts/infra/provision-alpha-ses-key.mjs`를 사용한다. Alpha 계정·인스턴스 태그·SES identity를 검증하고, 다른 사용자나 기존 파라미터가 있으면 중단한다. 정책 시뮬레이션과 SES 메일박스 시뮬레이터 확인을 수행한다. 실제 사용자 수신은 별도로 확인해야 한다.

## 키 교체

1. Alpha IAM 사용자의 두 키 제한과 기존 키 상태를 확인한다. 다른 사용자의 키를 삭제하지 않는다.
2. 같은 사용자에 새 키를 생성하고 새 키를 SSM의 두 `SecureString`에 함께 저장한다. 키 값은 채팅·파일·로그에 출력하지 않는다.
3. Alpha 배포가 새 값을 읽게 한 뒤 SES 메일박스 시뮬레이터와 실제 수신함으로 발송을 확인한다.
4. 새 키가 실제로 동작하는 것이 확인되면 이전 Alpha 전용 키만 비활성화·삭제한다. 실패하면 기존 키를 유지하고 파라미터와 배포 상태를 확인한다.

## 검증

1. Alpha에서 예약 테스트 번호로 인증을 요청하면 `devCode`가 내려오고 실제 문자는 발송되지 않아야 한다.
2. 본인의 실제 번호에는 `devCode`가 내려오지 않고 문자가 도착해야 한다. 직접 입력한 번호의 가입은 이 인증을 완료해야 한다.
3. 가입된 본인 이메일로 계정 찾기를 시작해 받은편지함·스팸함에서 Alpha 발신 메일을 확인하고, 코드를 입력해 로그인 방법이 표시되는지 본다.
4. 공급자 설정이 없거나 발송이 실패하면 성공 메시지 대신 오류가 표시되어야 한다. 테스트 계정은 다른 운영 데이터와 분리한다.
