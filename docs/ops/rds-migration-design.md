# RDS 이전 설계

컨테이너 Postgres → Amazon RDS for PostgreSQL 이전 계획. 2026-08-02 실측을 근거로 쓴다.

## 왜 옮기는가

성능 때문이 아니다. DB 는 24MB(v1) 이고 트래픽도 적어서 성능만 보면 RDS 는 과하다.
옮기는 이유는 **인스턴스를 버릴 수 있게 만들기 위해서**다.

지금은 데이터가 EC2 볼륨 안에 있어서 인스턴스를 함부로 교체·리사이즈할 수 없다. 그래서
"m/c 시리즈로 올리자"는 이야기가 계속 미뤄졌고, 배포는 매번 `teameet_v1_postgres` 컨테이너를
재생성한다(실측). 배포 스크립트가 아직 활발히 바뀌는 중이라 — 2026-08-02 하루에만 네 번
실패했다 — DB 의 운명이 배포 스크립트에 묶여 있는 상태 자체가 위험하다.

부수적으로 2GB 인스턴스에서 Postgres 두 개가 빠지면 메모리 압박도 준다(측정 시점 스왑 703MB
사용 중).

## 현재 상태 (2026-08-02 실측)

| 항목 | 값 |
|---|---|
| 엔진 | PostgreSQL **16.13** (`postgres:16-alpine`) |
| v1 DB | `teameet_v1` / user `teameet_v1` / **24MB** / 72 테이블 / 10,716 행 / FK 120 / 인덱스 278 |
| 레거시 DB | `teameet` / **43MB** (별도 스택, 정리 판단 대기) |
| 인스턴스 | t3a.small (2 vCPU / 2GB), `ap-northeast-2a` |
| VPC | **기본 VPC** `vpc-033c00b46c9514e71`, 서브넷 4개 **전부 퍼블릭**, 프라이빗 0개 |
| 앱 보안그룹 | `sg-0f194b59ba8cc2247` (인바운드 80/443 만) |
| 볼륨 암호화 | **없음** |

접속 문자열은 `deploy/docker-compose.prod.yml` 에서 조립된다:

```yaml
DATABASE_URL: postgresql://${V1_DB_USER:-teameet_v1}:${V1_DB_PASSWORD:-${DB_PASSWORD}}@v1_postgres:5432/${V1_DB_NAME:-teameet_v1}
```

호스트명 `v1_postgres` 만 RDS 엔드포인트로 바뀌면 되므로, 이전의 코드 변경 범위는 작다.

## 목표 구성

```
                     인터넷
                        │
                   [ teameet-alb ]         (기존)
                        │ 443
              ┌─────────┴─────────┐
              │  EC2 (퍼블릭 서브넷) │  sg-0f194b59ba8cc2247
              └─────────┬─────────┘
                        │ 5432  ← SG 소스로만 허용, CIDR 개방 없음
              ┌─────────┴─────────┐
              │  RDS (프라이빗)     │  teameet-rds-sg
              │  Multi-AZ 대비 2AZ  │
              └───────────────────┘
```

### 네트워크

기본 VPC 에 프라이빗 서브넷이 하나도 없으므로 새로 만든다. RDS 서브넷 그룹은 **최소 2개 AZ**
를 요구한다. 기존 서브넷이 `/20` 으로 172.31.0/16/32/48 을 쓰고 있으므로 그 뒤 대역을 쓴다.

| 용도 | AZ | 제안 CIDR |
|---|---|---|
| private-db-a | ap-northeast-2a | 172.31.64.0/24 |
| private-db-c | ap-northeast-2c | 172.31.65.0/24 |

라우팅 테이블은 **로컬 라우트만** 둔다 — RDS 는 아웃바운드 인터넷이 필요 없으므로 NAT 게이트웨이를
만들지 않는다(월 $40 가량 절약되고, 공격 표면도 줄어든다).

### 보안 그룹

`teameet-rds-sg` 인바운드는 **한 줄**이다.

```
5432/tcp  ←  source: sg-0f194b59ba8cc2247  (앱 보안그룹)
```

CIDR 기반 규칙을 두지 않는다. 이렇게 하면 IP 가 바뀌어도 규칙을 고칠 일이 없고, 인스턴스를
교체해도 같은 SG 를 붙이면 그대로 동작한다.

### 인스턴스 사양

| 항목 | 값 | 근거 |
|---|---|---|
| 클래스 | `db.t4g.micro` (2 vCPU / 1GB) | DB 24MB. 부족하면 무중단에 가깝게 스케일업 가능 |
| 스토리지 | gp3 20GB (최소) | 자동 확장 켜 둠 |
| **암호화** | **활성** | 현재 EBS 볼륨은 암호화가 없다 — 이전하면서 같이 고친다 |
| Multi-AZ | 처음엔 Single-AZ | 비용 2배. 트래픽이 붙으면 무중단 전환 가능 |
| 자동 백업 | 7일 + PITR | 지금은 존재하지 않는 기능 |
| 삭제 방지 | 활성 | |
| 엔진 | PostgreSQL 16.x | 현재 16.13 과 동일 계열 |

비용은 서울 리전 온디맨드 기준 대략 **월 $20 안팎**(인스턴스 + 스토리지, Single-AZ)으로 본다.
정확한 금액은 이전 직전에 요금표로 다시 확인할 것 — 이 문서의 숫자는 검증하지 않은 추정이다.

## 이전 절차

### 1단계 — 준비 (다운타임 없음)

1. 프라이빗 서브넷 2개 + 서브넷 그룹 + `teameet-rds-sg` 생성
2. RDS 인스턴스 생성, EC2 에서 `psql` 로 접속 확인
3. **리허설 이전**: 현재 S3 덤프를 RDS 에 복원해 테이블/행/FK 수가 맞는지 확인
   (`deploy/verify-prod-backup-restore.sh` 와 같은 검증을 RDS 대상으로 수행)
4. 앱을 RDS 로 붙인 상태로 **staging 검증** — 최소한 로그인·매치 조회·관리자 화면

### 2단계 — 전환 (다운타임 ~5분)

DB 가 24MB 라 논리 복제 같은 무중단 기법은 과하다. 짧은 점검창이 더 단순하고 안전하다.

1. 점검 공지 후 앱 컨테이너 정지 (`v1_api`, `v1_web`) — DB 컨테이너는 살려 둔다
2. 최종 `pg_dump` → RDS 로 복원
3. 행 수 대조 (원본 == RDS)
4. `V1_DB_HOST` 계열 변수를 RDS 엔드포인트로 전환하고 앱 기동
5. 헬스체크 + 실제 화면 확인

### 3단계 — 정리 (전환 후 최소 7일 뒤)

- `deploy/docker-compose.prod.yml` 에서 `v1_postgres` 서비스 제거
- `deploy/backup-prod-db.sh` 의 접속 대상을 RDS 엔드포인트로 변경
  (스크립트를 `pg_dump` 기반으로 남겨 둔 이유가 이것이다 — 접속 대상만 바뀐다)
- 컨테이너 Postgres 볼륨은 **바로 지우지 않는다.** 롤백 창이 끝난 뒤에 지운다

## 롤백

전환 후 문제가 생기면 되돌리는 비용이 낮아야 한다.

- 컨테이너 Postgres 를 **정지만 하고 볼륨은 유지**한다. `DATABASE_URL` 을 되돌리고 컨테이너를
  다시 올리면 전환 직전 상태로 복귀한다.
- 단, 전환 이후 RDS 에 쌓인 데이터는 그 방식으로 되돌아오지 않는다. 그래서 전환 직후에는
  쓰기가 적은 시간대를 고르고, 이상 징후를 빨리 판단해야 한다.
- 롤백 판단 시한을 미리 정해 둔다(예: 전환 후 30분 내 결정).

## 이전 후에도 남는 것

- `deploy/backup-prod-db.sh` 는 계속 쓴다. RDS 자동 백업은 인스턴스 단위 복구이고, **테이블
  단위 복구나 계정 밖으로의 사본**은 여전히 논리 덤프가 필요하다.
- EBS 스냅샷은 유지하되 역할이 바뀐다 — DB 가 아니라 OS·nginx 설정·인증서를 위한 것이 된다.
- 레거시 스택(`teameet` 43MB)은 이 계획에 포함하지 않았다. 정리할지 함께 옮길지 먼저 결정해야 한다.
