### 네이버 — 검색 결과 설명 20건 중 16건이 오류 문구

네이버에서 `site:teameet.co.kr` 첫 페이지 20건 중 16건(팀 1·대회 상세 1·시상 1·결과 1·대진표 3·경기 상세 9)의 설명이 「…정보를 불러오지 못했어요」 같은 오류 문구다. 나머지 4건은 목록·랜딩·용어집 주소다(저장한 검색 화면을 항목별로 다시 세어 확인했다). 같은 주소를 네이버 로봇(Yeti) 모양 요청으로 받으면 200·제목·설명·canonical 이 정상이고 색인 허용이며 보이는 본문에 오류 문구가 없다. 그래서 예전에 오류 상태로 그려진 화면이 네이버 쪽에 남은 것으로 보인다(추정). 원인은 확정되지 않았다 — 네이버가 JS 를 실행해 화면 안에서 데이터를 다시 불러오다 실패하는 경우는 이 측정으로 배제되지 않는다. 재수집 요청 뒤와 운영 반영 뒤에 같은 검색을 다시 세어 본다.

- 이미 고친 원인이 있다. 서버 렌더에서는 데이터를 받아 오지 않아 `isLoading` 이 false 로 남고, 그 상태가 오류 분기로 떨어져 첫 HTML 에 오류 문구가 실렸다. 판정을 `isPending` 으로 바꾼 커밋이 대회 상세·하위 화면(`68be318f8`, 2026-09-27), 대진표 일정·팀 전적(`201aeed76`, 2026-09-27), 경기 상세(`24510c3d5`, 2026-10-17)로 세 번 있었다. 마지막 고침으로부터 27일이 지난 11-13 에도 16/20 이 남아 있다는 것이 핵심 사실이다. 지금 코드에 남은 「불러오지 못했어요」 화면은 API 호출이 실제로 실패했을 때의 정상 실패 분기이고, 이번 수정 묶음에서 바꾸지 않는다.
- 서치어드바이저에 로그인하지 못해 마지막 수집 시각·사이트맵 처리 상태는 확인하지 못했다. 11-17 에 읽은 값은 5-4 에 있다. 재수집 요청은 외부 요청이라 사용자 확인 뒤에 한다(Task 20261135 의 G11).

### 다음·Bing — 다음은 등록 검토 중, Bing 은 소유 확인 완료(11-17 밤 기준)

- **다음(Daum)**: 다음 검색등록의 「등록조회」(로그인 불필요)에서 `teameet.co.kr`·`https://teameet.co.kr`·`www.teameet.co.kr` 모두 **미등록 사이트**였다(등록된 사이트 `daum.net` 은 「카카오에서 등록」으로 나오는 것을 대조로 확인). 다음 검색의 `site:teameet.co.kr` 결과도 0건이다. 이 조회는 사이트검색 등록부 기준이라 웹문서 색인과 같은 것인지는 확인하지 못했다. 등록 단계는 아래 6-4 에 더했다. 11-15 에 다시 조회해도 같았다(5-4). 11-17 밤에 신청했고 등록조회 상태는 「검토중인 사이트」다(5-4).
- **Bing**: 웹마스터 도구에 로그인 세션이 없어 등록 여부를 **확인하지 못했다.** 운영 HTML 에 소유확인 메타(`msvalidate.01`)는 있지만 이것이 등록 완료를 뜻하지는 않는다. Bing 검색 자체에는 `/landing`·`/tournaments` 등이 색인돼 있다. 11-17 낮에도 읽지 못했으나 같은 날 밤에 로그인해 보니 사이트는 2026-09-27 부터 추가돼 있었고 소유 확인만 안 된 상태였다. 메타 태그 방식으로 소유 확인을 마쳤다(5-4).

### 그 밖에 측정한 응답 동작

- `/tournaments/<id>/schedule`: 실제 대회와 없는 id 가 같은 응답을 낸다 — 200, 제목 「스포츠 대회 | Teameet」, 본문 0자, canonical `/tournaments`, 검색 제외 표시 없음(색인 허용). 사이트맵과 대회 상세 HTML 어디에도 이 주소로 가는 링크는 없다. 설정 이동(308, `/tournaments/<id>/bracket` 으로 영구 이동)으로 바꾸는 중이다(Task 20261135). 이 문서가 먼저 머지되므로 위 내용은 바꾸기 전의 측정값이다.
- http→https 이동 응답의 `Location` 에 `:443` 이 붙는다(예: `https://teameet.co.kr:443/landing`). 응답 헤더가 `Server: awselb/2.0` 이라 nginx 가 아니라 앞단 로드밸런서의 80→443 규칙이 만든 것이고, 브라우저·검색엔진이 기본 포트로 정규화하므로 동작에 영향이 없다. 바꾸려면 nginx 가 아니라 로드밸런서 규칙을 봐야 한다.

## 2026-10-15 실제 검색 재확인과 후속 수정

- 코드 변경: `/home`은 수집만 허용하고 noindex를 유지한다. `/landing`의 제목에 한글 브랜드와 실제 서비스 내용을 넣는다. alpha는 검색 봇이 HTTP noindex를 읽게 하고 그 외 크롤러는 차단하며 sitemap/RSS를 404로 처리한다. PR #1842의 alpha `8deac7bc16382b85615f70d98c1a91cd5ae858a7`에서 실측 완료. 운영은 배포 대기다.
- 실제 운영 브라우저에서 `/landing`의 page_view, `landing_cta_click {cta: hero_browse_team_matches}`, SPA 이동 후 `/team-matches`의 page_view를 관찰했다. 이동 후 제목도 `팀매치 찾기 | Teameet`으로 전송됐다. 이 한 동선에서 수동 page_view 중복 전송은 보이지 않았다.

## 용어 — 딱 다섯 개만

| 말 | 뜻 |
|---|---|
| **크롤러(crawler)** | 검색엔진이 보낸 로봇. 웹페이지를 자동으로 읽어 가요. **자바스크립트를 실행하지 않는 경우가 많아서**, 화면에는 보여도 로봇에겐 안 보이는 내용이 생깁니다. |
| **색인(index)** | 검색엔진이 "이 페이지를 검색 결과에 낼 수 있다"고 자기 목록에 넣어 둔 상태. 색인이 안 되면 아무리 좋은 페이지여도 검색에 안 나와요. |
| **구조화 데이터(JSON-LD)** | 페이지 안에 숨겨 넣는 "기계가 읽는 설명서". 사람 눈엔 안 보이고, 검색엔진에게 "이건 대회고, 언제 열리고, 참가비는 얼마"라고 알려줍니다. |
| **`llms.txt`** | ChatGPT·Claude 같은 생성형 AI 에게 주는 사이트 안내서. "우리는 무엇의 원출처이고, 어떤 페이지를 보면 되는지"를 적어 둡니다. |
| **AI 인용** | AI 가 답을 만들면서 출처로 우리 사이트를 다는 것. 클릭 유입으로 이어집니다. |

## 2. 승(承) — 왜 그랬나

세 목록 페이지가 이런 모양이었습니다.

```tsx
<Suspense fallback={null}>   {/* ← 로봇이 받는 자리가 '아무것도 없음' */}
  <MatchListPageClient />    {/* 브라우저에서만 그려지는 부분 */}
</Suspense>
```

`fallback={null}` 은 "브라우저가 그리기 전까지 **아무것도 두지 마라**"는 뜻입니다. 사람은
0.5초 뒤 목록을 보지만, 로봇은 그 0.5초를 기다려 주지 않아요. 그래서 빈 종이만 가져갑니다.

구조화 데이터와 `llms.txt` 는 애초에 만든 적이 없었습니다.

## 3. 전(轉) — 무엇을 골랐고, 무엇을 포기했나

### 고른 방법: 서버가 첫 화면을 미리 그려 둔다

로봇이 요청하면 **서버에서 목록 20건을 미리 받아 그려서** 보냅니다. 브라우저가 준비되면
원래의 필터·검색이 붙은 화면으로 바뀌므로 **사람이 보는 최종 화면은 그대로**입니다.

| | 장점 | 단점 |
|---|---|---|
| **바꾸기 전** (`fallback={null}`) | 서버가 할 일이 없어 응답이 가볍다. 목록 데이터를 서버에서 안 받으니 API 부하도 없다 | **로봇에게 빈 페이지**. 검색·AI 어디에도 내용이 안 잡힌다 |
| **바꾼 뒤** (서버 프리렌더) | 로봇이 실제 목록을 읽는다. 사람도 로딩 중 빈 화면 대신 목록을 본다 | 서버가 목록 API 를 한 번 더 부른다(5분 캐시로 완화). **캐시가 식기 전 잠깐 옛 목록**이 보일 수 있다 |

5분 캐시(ISR)를 고른 이유는, 목록이 자주 바뀌는데 매 요청마다 서버가 API 를 부르면 부담이
커지기 때문입니다. 대신 **최대 5분까지 옛 목록**이 로봇에게 갈 수 있다는 대가를 받아들였습니다.
대회·팀 상세는 원래대로 매번 최신입니다.

### 하지 않은 것과 이유

- **목록 페이지에 `<h1>` 추가** — 사람이 보는 화면이 바뀌므로 디자인 3안 검토가 먼저입니다.
- **AI 크롤러 전체 허용(`Allow: /`)** — 그렇게 하면 `/admin`·`/my`·`/chat` 같은 **비공개 화면까지**
  AI 에 넘어갑니다. 지금과 똑같은 공개 범위만 열었습니다.
- **화면에 없는 값을 구조화 데이터에 넣기** — 예를 들어 "참가 팀 8팀"을 넣고 싶었지만,
  그 자리에 쓸 수 있는 표준 항목이 "최대 **참석 인원**"뿐이라 **8팀이 8명으로 읽힙니다.**
  맞지 않는 칸에 억지로 넣으면 검색엔진이 우리를 못 믿게 되므로 뺐습니다.

**확인한 것 — 코드와 운영 응답(읽기만)**

- 운영 판(main) 코드는 거의 모든 화면의 푸터에 약관 5개 링크를 두고, 링크마다 `?from=<지금 주소>` 꼬리를 붙여 서버 HTML 로 내보낸다. 푸터는 모바일에서 CSS 로 숨길 뿐 HTML 에는 항상 들어 있다. 꼬리 값이 화면마다 달라서 화면이 하나 늘 때마다 새 약관 주소가 5개씩 생긴다.
- 운영 서버 HTML 로 확인했다. `/teams` 에 `from=` 이 든 링크가 6개(약관 5 + 알림 1), `/tournaments` 에 28개(대회 카드 20 + 약관 5 + 알림 2 + `/events` 1)다. dev 코드를 서빙하는 alpha 는 `/teams` 0개, `/tournaments` 21개(카드 20 + `/events` 1)다.
- 운영 `/terms` 는 쿼리를 읽지 않는 정적 껍데기라 꼬리가 달라도 같은 응답(24,319바이트)이 나간다. `/terms` 와 `/terms?document=privacy&from=%2Fteams` 를 직접 받아 본문이 바이트 단위로 같았다. 로봇은 약관 내용이 아니라 껍데기를 받고 있다. 이 응답에는 `noindex, nofollow, noarchive` 가 붙어 있는데도 24,164건이 읽혔다 — noindex 는 읽기 자체를 줄이지 않는다.
- 운영 `robots.txt` 는 GPTBot 을 따로 막지 않고 13개 그룹이 같은 규칙이다. `from=`·쿼리를 막는 줄과 `Crawl-delay` 는 없다.
- 새 꼬리 주소가 생기는 것은 dev 의 #2376 이 막는다. 푸터·알림 링크가 서버 HTML 에는 `from` 없이 나가고 사용자가 왼쪽 클릭할 때만 지금 주소를 붙인다(alpha 서버 HTML 로 확인). 카드·상세 안 링크의 `from=` 은 dev 에도 그대로다(Task 20261135 의 G15 로 미룬 부분, 링크를 만드는 파일 65개).

**추정**

- 위 코드와 응답이 합쳐져 같은 약관이 화면 수만큼의 다른 주소로 퍼지고 GPTBot 이 그 링크를 따라간다는 설명이 읽기 구성(꼬리 달린 `/terms` 약 71%, `from=` 이 든 줄 약 98%)과 맞는다. 운영 코드의 꼬리 체인 함수를 그대로 복사해 푸터 링크를 따라가 닿는 서로 다른 약관 주소를 세어 보니 시작 화면 1개에 530, 10개에 2,375, 50개에 10,575, 200개에 41,325 였다. 체인에 4단계 한도가 있어 끝은 있지만 실제 크기는 10만 단위로 짐작한다. 접속 기록 원문의 꼬리 값과 서로 다른 주소의 수는 보지 않았다(확인 못 함).
- 서버 부담은 호출 수일 뿐이다. 낮 구간 기준으로 GPTBot 은 분당 약 119건이고 그중 `/terms?…` 가 분당 약 90건이다(저녁 구간은 시간 폭을 재지 않아 같은 4시간 반을 가정한 값). 앱 프록시(`proxy.ts`)가 상세 주소 요청마다 캐시 없이 API 를 한 번 부르므로 `/teams/:id`·`/tournaments/:id` 계열 6,643건은 분당 약 25건의 API 호출이다. 서버 CPU·DB 부하는 재지 않았다.
- GPTBot 의 읽기가 꼬리 주소에 쓰이는 만큼 정식 주소를 읽는 몫이 줄 수 있다. 크롤 한도가 주소 수에 묶여 있는지는 알 수 없어 이 인과는 증명하지 못했다. 다른 로봇은 낮 구간 표대로 거의 읽지 않아, 이 쏠림은 GPTBot 한 곳이 만든다.

**확인하지 못한 것**: GPTBot 이 robots 의 와일드카드(`*`)를 어떻게 읽는지와 바뀐 robots 를 언제부터 따르는지, 옛 주소를 몇 주 동안 읽을지, 이 요청이 모두 진짜 OpenAI 인지(사용자 에이전트 글자로 센 값이고 접속 IP 는 대조하지 않았다), 읽기 쏠림이 ChatGPT 검색·학습 노출에 준 영향이다.

**남는 것**: dev 의 #2376 을 운영에 올리면 새 꼬리 주소는 멈추지만, 로봇이 이미 아는 주소를 읽는 양은 줄지 않고 읽기의 나머지 약 29%(팀·대회 상세 쪽, 카드·상세 안 링크의 `from=` 으로 보인다 — 추정)도 그대로다. 또 dev 쪽 `/terms` 는 요청마다 서버가 약관을 그리도록 바뀌어(#2375) 옛 주소 방문 한 건이 지금보다 비싸진다(alpha 에서 한 번 잰 응답 시간 76~136ms). 고칠 방법 후보와 결정은 Task 20261135 의 「5차 답 뒤 실행」에 있고 사용자 결정 대기다.

- **다음(Daum) 신규등록 신청**: 11-17 밤(22:43 이후)에 사용자가 직접 지시해 신청을 마쳤다. 칸은 제목 「팀밋(Teameet)」, 분류 「스포츠, 레저>생활체육」(분류 검색에서 「생활체육」을 쳐서 골랐다), 설명 「생활체육 팀 매칭, 아마추어 대회, 경기 기록」, 설명-품목 「팀 매칭, 선수 매칭, 아마추어 대회, 경기 결과, 선수 카드」이고, 주소는 화면이 고정한 `http://teameet.co.kr` 이다. 지역·카카오톡 채널 칸은 비웠다. 필수 동의 두 칸은 앞선 실행에서 읽어 둔 원문과 글자를 맞대 같은 것을 확인하고 동의했다(선택 동의는 없었다). 신청자 이름·이메일은 카카오 계정의 값을 넣었고 이 문서에는 적지 않는다. 등록 변경·삭제 때 본인 확인에 같은 이름·이메일을 쓴다. 접수 완료 화면이 떴고 접수 번호는 화면에 없다. 등록조회 상태는 **「검토중인 사이트」**다(「검토가 완료된 이후에 등록/수정/삭제 신청이 가능합니다」 안내). 심사 결과는 신청자 이메일로 오고 아직 모른다(확인 못 함). **거부될 위험이 조금 남는다(추정).** 가이드에 「신청한 사이트 제목과 사이트상에서 확인되는 제목이 일치해야 합니다」와 「특정 사용자만 볼 수 있도록 제한하거나 비공개 상태일 경우 등록되지 않습니다」가 있는데, 운영 메인 주소의 화면 제목은 `Teameet` 이고 한글 「팀밋」은 화면 글자에 없으며(구조화 데이터의 `alternateName` 에만 있다) 메인 주소는 `noindex, follow` 이고 로그인 화면으로 이어진다. 이 점을 심사가 어떻게 보는지는 확인하지 못했다.
- **Bing 웹마스터 소유 확인**: 사이트(`teameet.co.kr`)는 2026-09-27 에 이미 추가돼 있었고 소유 확인이 안 된 상태였다. 로그인하면 「소유 확인 대기」 창이 떴고 이 창이 사이트맵·URL 검사 화면까지 막았다. 이 프로필의 구글 계정이 이전에 Bing 웹마스터와 연결돼 있어 동의·계정 고르기 화면 없이 들어갔고 새 계정은 만들지 않았다. 운영 HTML 의 `/`·`/landing` 둘 다에 확인용 메타 태그(`msvalidate.01`)가 하나씩 있고 두 값이 같으며 Bing 이 보여 준 값과도 같은 것을 확인한 뒤(해시 앞자리로만 견주었고 값은 적지 않는다) 메타 태그 방식의 「Verify」를 한 번 눌러 **소유 확인을 마쳤다.**
  - 확인 직후에 읽은 것: 제출된 사이트맵이 없다(발견 주소 수가 비어 있어 구글 사이트맵 발견 598 과 견줄 값이 아직 없다). `/landing` 은 색인돼 있고(「Indexed successfully」, 발견 2026-07-30, 마지막 크롤 2026-11-15) 11-13 에 적은 「Bing 검색에 `/landing` 이 색인돼 있다」와 맞는다. 이 검사에서 SEO 지적은 1건(이미지 Alt 속성 누락 10곳)이다. 색인 요약과 검색 성과는 확인 직후라 비어 있고 Bing 안내로는 최대 48시간 뒤에 채워진다. 11-19 밤 이후 다시 읽어 이 문서에 적는다.
  - 하지 않은 것: 사이트맵 제출·색인 요청·사이트 추가·구글 서치 콘솔에서 가져오기·다른 확인 방식. 사이트맵 제출은 이번 범위 밖이라 하지 않았고 Bing 사이트 홈이 제출을 권한다 — 제출 여부는 사용자 결정 대기다.
  - **확인용 메타 태그를 운영 HTML 에서 지우면 안 된다.** Bing 안내가 확인이 끝난 뒤에도 지우지 말라고 한다.

## 6. 사람이 해야 하는 등록 — 계정이 필요해 자동화할 수 없습니다

### 6-1. Bing 웹마스터도구 (10분, **가장 먼저**)

> **왜 중요한가**: ChatGPT 검색과 Bing Copilot 은 **Bing 색인**에서 답을 꺼냅니다.
> 여기 등록이 안 돼 있으면 AI 검색 인용 경로의 절반이 닫힌 채로 남습니다.

1. https://www.bing.com/webmasters 접속 → Microsoft 계정으로 로그인
2. **"Google Search Console에서 가져오기"** 선택 — 소유 확인과 사이트맵까지 한 번에 넘어옵니다
   (GSC 가 아직 없으면 `teameet.co.kr` 을 직접 추가하고 DNS 또는 HTML 태그로 소유 확인)
3. 왼쪽 메뉴 **사이트맵** → `https://teameet.co.kr/sitemap.xml` 제출
4. **IndexNow** 메뉴에서 키를 발급받아 두기 (새 페이지를 즉시 알리는 기능. 연동은 개발 작업)
   — 2026-11-13 현재 저장소에 IndexNow 코드는 없고 키 발급을 기다리는 상태다. Bing 등록 확인(Task 20261135 의 G11) 때 함께 본다.
5. 확인: Bing 검색창에 `site:teameet.co.kr` → 결과가 나오면 색인된 것

2026-11-17 밤 현황: 사이트는 09-27 에 이미 추가돼 있었고 메타 태그 방식으로 소유 확인을 마쳐 2번은 더 할 일이 없다. 3번(사이트맵 제출)은 아직 하지 않았다(5-4).

### 6-2. 네이버 서치어드바이저 (15분)

> **왜 중요한가**: 한국 생활체육 서비스는 검색 유입의 상당 부분이 네이버입니다.
> 네이버 **AI 브리핑**(검색 상단 AI 요약)이 출처를 다는 것도 여기 등록이 전제입니다.

1. https://searchadvisor.naver.com 접속 → 네이버 계정 로그인
2. **웹마스터 도구** → 사이트 등록에 `https://teameet.co.kr` 입력
3. 소유 확인 — HTML 파일 업로드 또는 메타태그 중 선택
   (메타태그 방식이면 태그 값을 개발자에게 전달해 주세요. 코드에 넣어야 합니다)
4. **요청 → 사이트맵 제출**: `https://teameet.co.kr/sitemap.xml`
5. **검증 → robots.txt**: `Yeti`(네이버 크롤러)가 허용돼 있는지 확인
   (이번 작업으로 이미 명시해 뒀습니다)
6. **요청 → 웹페이지 수집**: 대회 상세처럼 중요한 새 페이지는 여기서 수동 수집 요청
7. 등록 후 **주 1회** 〈리포트 → 사이트 진단 / 검색 노출〉 확인

### 6-3. Google Search Console (이미 있으면 건너뜀)

1. https://search.google.com/search-console → 속성 추가 → `teameet.co.kr`
2. 사이트맵 제출: `sitemap.xml`
3. **URL 검사** 도구로 `/teams`·`/matches` 를 넣어 "페이지 가져오기" → 렌더된 HTML 에
   목록이 보이는지 확인 (이번 작업의 효과를 구글 쪽에서 직접 확인하는 방법입니다)

### 6-4. 다음(Daum) 검색등록 (10분)

> **왜 필요한가**: 2026-11-13 등록조회에서 `teameet.co.kr` 이 **미등록 사이트**였고, 다음 검색의
> `site:teameet.co.kr` 결과도 0건이었습니다. 등록이 이 0건의 원인인지(등록부와 웹문서 색인이
> 같은 것인지)는 아직 모르지만, 신청은 사람이 하는 일이라 먼저 해 둘 가치가 있습니다.

1. https://register.search.daum.net 의 **등록조회**(로그인 없이 가능)로 현재 상태를 먼저 적어 둡니다.
2. 카카오 계정으로 로그인해 **신규등록 → 사이트검색**에 `https://teameet.co.kr` 을 신청합니다.
   처리 결과는 신청 때 적은 이메일로 온다고 화면에 안내돼 있습니다.
3. 다음 등록 가이드는 영리 사이트에 하단의 업체명·주소·연락처·대표자명·사업자등록번호 표기를 요구합니다.
   `/landing` 푸터에는 사업자 정보가 있고, 통신판매업 신고번호 표기가 필요한지는 Task 20261135 의 G19(법무 확인)에서 다룹니다.
4. 며칠 뒤 같은 **등록조회**로 상태가 「미등록」에서 바뀌었는지, 다음 검색에서 `site:teameet.co.kr` 가
   나오는지 확인하고 이 문서에 날짜와 함께 적습니다.

외부 사이트에 신청하는 일이라 사용자 확인 뒤에 합니다(Task 20261135 의 G11).

2026-11-17 밤 현황: 2번까지 마쳤다. 신청했고 등록조회 상태는 「검토중인 사이트」다(5-4). 4번의 재조회는 심사 결과가 나온 뒤에 한다.

## 7. 읽는 법 — 숫자가 움직이면 무슨 뜻인가

- **노출이 먼저, 클릭은 나중**: 구조를 고치면 **노출(검색 결과에 뜬 횟수)**부터 움직입니다.

  다음에 만들 페이지입니다.

## 8. 함정 — 측정하다 틀리기 쉬운 곳

  통과시킵니다. 값이 아니라 **값의 날짜**를 함께 보세요.
