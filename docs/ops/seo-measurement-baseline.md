# 검색·AI 노출 측정 — 기준선과 재측정 절차

## 2026-10-12 운영 점검

현재 작업: [Task 20261072](../../.github/tasks/20261072-production-search-ga4.md). 아래의 9월 기준선은 과거 기록이다.

- Google Search Console에서 운영 URL 접두어 `https://teameet.co.kr/`의 소유권을 기존 HTML 메타로 확인했다. `/landing`은 이미 색인돼 있고, `/home`은 **색인이 생성되었으나 robots.txt에 의해 차단됨**으로 표시된다. 수집을 막으면 noindex도 읽히지 않아 URL만 검색에 남을 수 있다.
- Google/Yeti UA의 운영 `/sitemap.xml` 응답은 200 `application/xml`, 271개 고유 운영 URL이다. 제출 직후의 **사이트맵을 읽을 수 없음** 상태는 처리 대기 후 해소됐다. 10월 12일 05:41 Search Console에서 **성공**, 읽은 날짜 10/12, 발견 URL 271을 확인했다. XML 문법·고유 URL·운영 호스트도 검증했으며 재제출하지 않았다.
- 네이버 계정에는 운영 사이트가 9월 27일자로 등록돼 있으나 소유확인 미완료였다. 기존 운영 HTML의 인증 태그로 소유확인을 마쳤다. 10월 12일 운영 사이트맵(05:32:17), 공지 RSS `/notices/feed.xml`(05:34:13), `/landing` 수집 요청(05:34:32)이 각각 등록 목록에 나타나는 것을 확인했다. 시각은 네이버 화면 표시 기준이다. alpha는 제출하지 않았다. 요청 접수는 검색 색인 완료와 다르다.
- 코드 변경: `/home`은 수집만 허용하고 noindex를 유지한다. `/landing`의 제목에 한글 브랜드와 실제 서비스 내용을 넣는다. alpha는 검색 봇이 HTTP noindex를 읽게 하고 그 외 크롤러는 차단하며 sitemap/RSS를 404로 처리한다. PR #1842의 alpha `8deac7bc16382b85615f70d98c1a91cd5ae858a7`에서 실측 완료. 운영은 배포 대기다.
- 실제 운영 브라우저에서 `/landing`의 page_view, `landing_cta_click {cta: hero_browse_team_matches}`, SPA 이동 후 `/team-matches`의 page_view를 관찰했다. 이동 후 제목도 `팀매치 찾기 | Teameet`으로 전송됐다. 이 한 동선에서 수동 page_view 중복 전송은 보이지 않았다.
- GA4 속성 `448147119`에 alpha와 운영 스트림이 같이 있다. 운영 스트림은 `teameet-prod` / `15280614121` / `G-LCZ6BNMMHV`다. **운영 사이트만 · teameet-prod** 비교를 저장했고, 실제 조건은 streamId `15280614121` 일치다.
- GA4에 이벤트 범위 맞춤 측정기준 `cta`(랜딩 CTA 위치), `destination`(홈 이동 목적지), `destination_type`(홈 이동 화면 유형)을 저장했다. 신규 홈 이동 이벤트는 코드 배포 뒤 수집된다.
- 운영 Google 태그의 원치 않는 추천 목록에는 이미 `accounts.kakao.com`, `kauth.kakao.com` 정확 일치 규칙이 있어 유지했다. 아래 기간 중 `kauth.kakao.com / referral` 127세션이 관찰됐지만 과거 데이터만으로 현재 설정이 없다고 판단하지 않았다.

GA4 Internal Traffic 필터는 Testing 상태다. 원본 수집을 보존하면서 운영 스트림과 `testDataFilterName=Internal Traffic` 제외 조건을 결합한 **운영 · 내부 트래픽 제외** 비교(ID `16108290729`)를 저장·적용했다. 식별되지 않은 내부 방문까지 제거됐다고 해석하지 않는다.

기간 합계는 과거 계측 변경을 포함하므로 이벤트 수 차이만으로 중복·누락을 단정하지 않는다. 랜딩 방문 사용자 분모와 동일 여정 연결을 확인하지 않았으므로 CTA 클릭 수를 가입 전환율로 해석하지 않는다. 새 맞춤 측정기준의 과거 데이터 소급 집계를 약속하지 않는다.

배포 후: 운영 robots·noindex·메타 및 alpha noindex/사이트맵 404를 재확인하고, DebugView에서 새 홈 이동 이벤트의 목적지와 중복 여부를 확인한다. 검색 효과는 **실제 운영 배포일 +14일, +30일**에 같은 기간·속성·필터로 비교한다. 순위 상승이나 즉시 검색 결과 변경을 보장하지 않는다.

## 용어 — 딱 다섯 개만

| 말 | 뜻 |
|---|---|
| **크롤러(crawler)** | 검색엔진이 보낸 로봇. 웹페이지를 자동으로 읽어 가요. **자바스크립트를 실행하지 않는 경우가 많아서**, 화면에는 보여도 로봇에겐 안 보이는 내용이 생깁니다. |
| **색인(index)** | 검색엔진이 "이 페이지를 검색 결과에 낼 수 있다"고 자기 목록에 넣어 둔 상태. 색인이 안 되면 아무리 좋은 페이지여도 검색에 안 나와요. |
| **구조화 데이터(JSON-LD)** | 페이지 안에 숨겨 넣는 "기계가 읽는 설명서". 사람 눈엔 안 보이고, 검색엔진에게 "이건 대회고, 언제 열리고, 참가비는 얼마"라고 알려줍니다. |
| **`llms.txt`** | ChatGPT·Claude 같은 생성형 AI 에게 주는 사이트 안내서. "우리는 무엇의 원출처이고, 어떤 페이지를 보면 되는지"를 적어 둡니다. |
| **AI 인용** | AI 가 답을 만들면서 출처로 우리 사이트를 다는 것. 클릭 유입으로 이어집니다. |

## 1. 기(起) — 무엇이 문제였나

2026-09-01, 프로덕션(`teameet.co.kr`)을 **크롤러의 눈으로** 실측한 결과입니다.
브라우저가 아니라 `curl` 로 받은 HTML, 즉 로봇이 실제로 보는 것을 셌습니다.

| 페이지 | `<h1>` | 종목 단어(풋살·농구…) | 구조화 데이터 |
|---|---|---|---|
| `/landing` | 1개 | 36회 | **0개** |
| `/tournaments` | 1개 | 0회 | **0개** |
| `/matches` | **0개** | **0회** | **0개** |
| `/teams` | **0개** | **0회** | **0개** |
| `/team-matches` | **0개** | **0회** | **0개** |

목록 세 개는 **로봇에게 빈 종이**였습니다. 매치도, 팀 이름도, 종목 단어도 한 번 안 나옵니다.
사람이 브라우저로 열면 잘 보이는데, 그건 자바스크립트가 그린 것이라 로봇은 못 봅니다.

그 외:

- `robots.txt` 의 크롤러 규칙: **`*` 하나뿐** (AI 크롤러·네이버 봇에 대한 정책 없음)
- `/llms.txt`: **404** (AI 에게 줄 안내서가 없음)
- `sitemap.xml`: 71개 URL (팀 44 · 대회 21) — 이건 잘 돼 있었습니다

## 2. 승(承) — 왜 그랬나

세 목록 페이지가 이런 모양이었습니다.

```tsx
<Suspense fallback={null}>   {/* ← 로봇이 받는 자리가 '아무것도 없음' */}
  <MatchListPageClient />    {/* 브라우저에서만 그려지는 부분 */}
</Suspense>
```

`fallback={null}` 은 "브라우저가 그리기 전까지 **아무것도 두지 마라**"는 뜻입니다. 사람은
0.5초 뒤 목록을 보지만, 로봇은 그 0.5초를 기다려 주지 않아요. 그래서 빈 종이만 가져갑니다.

구조화 데이터와 `llms.txt` 는 애초에 만든 적이 없었습니다.

## 3. 전(轉) — 무엇을 골랐고, 무엇을 포기했나

### 고른 방법: 서버가 첫 화면을 미리 그려 둔다

로봇이 요청하면 **서버에서 목록 20건을 미리 받아 그려서** 보냅니다. 브라우저가 준비되면
원래의 필터·검색이 붙은 화면으로 바뀌므로 **사람이 보는 최종 화면은 그대로**입니다.

| | 장점 | 단점 |
|---|---|---|
| **바꾸기 전** (`fallback={null}`) | 서버가 할 일이 없어 응답이 가볍다. 목록 데이터를 서버에서 안 받으니 API 부하도 없다 | **로봇에게 빈 페이지**. 검색·AI 어디에도 내용이 안 잡힌다 |
| **바꾼 뒤** (서버 프리렌더) | 로봇이 실제 목록을 읽는다. 사람도 로딩 중 빈 화면 대신 목록을 본다 | 서버가 목록 API 를 한 번 더 부른다(5분 캐시로 완화). **캐시가 식기 전 잠깐 옛 목록**이 보일 수 있다 |

5분 캐시(ISR)를 고른 이유는, 목록이 자주 바뀌는데 매 요청마다 서버가 API 를 부르면 부담이
커지기 때문입니다. 대신 **최대 5분까지 옛 목록**이 로봇에게 갈 수 있다는 대가를 받아들였습니다.
대회·팀 상세는 원래대로 매번 최신입니다.

### 하지 않은 것과 이유

- **목록 페이지에 `<h1>` 추가** — 사람이 보는 화면이 바뀌므로 디자인 3안 검토가 먼저입니다.
- **AI 크롤러 전체 허용(`Allow: /`)** — 그렇게 하면 `/admin`·`/my`·`/chat` 같은 **비공개 화면까지**
  AI 에 넘어갑니다. 지금과 똑같은 공개 범위만 열었습니다.
- **화면에 없는 값을 구조화 데이터에 넣기** — 예를 들어 "참가 팀 8팀"을 넣고 싶었지만,
  그 자리에 쓸 수 있는 표준 항목이 "최대 **참석 인원**"뿐이라 **8팀이 8명으로 읽힙니다.**
  맞지 않는 칸에 억지로 넣으면 검색엔진이 우리를 못 믿게 되므로 뺐습니다.

> 모델이 "학습으로 아는 것"인지 알 수 있어요. ① 모른다 ② 틀리게 안다 ③ 맞게 안다 중 하나로 적습니다.

### 5-4. 색인 수

검색창에 `site:teameet.co.kr` 을 넣으면 대략의 색인 페이지 수가 나옵니다(구글·빙 각각).

## 6. 사람이 해야 하는 등록 — 계정이 필요해 자동화할 수 없습니다

### 6-1. Bing 웹마스터도구 (10분, **가장 먼저**)

> **왜 중요한가**: ChatGPT 검색과 Bing Copilot 은 **Bing 색인**에서 답을 꺼냅니다.
> 여기 등록이 안 돼 있으면 AI 검색 인용 경로의 절반이 닫힌 채로 남습니다.

1. https://www.bing.com/webmasters 접속 → Microsoft 계정으로 로그인
2. **"Google Search Console에서 가져오기"** 선택 — 소유 확인과 사이트맵까지 한 번에 넘어옵니다
   (GSC 가 아직 없으면 `teameet.co.kr` 을 직접 추가하고 DNS 또는 HTML 태그로 소유 확인)
3. 왼쪽 메뉴 **사이트맵** → `https://teameet.co.kr/sitemap.xml` 제출
4. **IndexNow** 메뉴에서 키를 발급받아 두기 (새 페이지를 즉시 알리는 기능. 연동은 개발 작업)
5. 확인: Bing 검색창에 `site:teameet.co.kr` → 결과가 나오면 색인된 것

### 6-2. 네이버 서치어드바이저 (15분)

> **왜 중요한가**: 한국 생활체육 서비스는 검색 유입의 상당 부분이 네이버입니다.
> 네이버 **AI 브리핑**(검색 상단 AI 요약)이 출처를 다는 것도 여기 등록이 전제입니다.

1. https://searchadvisor.naver.com 접속 → 네이버 계정 로그인
2. **웹마스터 도구** → 사이트 등록에 `https://teameet.co.kr` 입력
3. 소유 확인 — HTML 파일 업로드 또는 메타태그 중 선택
   (메타태그 방식이면 태그 값을 개발자에게 전달해 주세요. 코드에 넣어야 합니다)
4. **요청 → 사이트맵 제출**: `https://teameet.co.kr/sitemap.xml`
5. **검증 → robots.txt**: `Yeti`(네이버 크롤러)가 허용돼 있는지 확인
   (이번 작업으로 이미 명시해 뒀습니다)
6. **요청 → 웹페이지 수집**: 대회 상세처럼 중요한 새 페이지는 여기서 수동 수집 요청
7. 등록 후 **주 1회** 〈리포트 → 사이트 진단 / 검색 노출〉 확인

### 6-3. Google Search Console (이미 있으면 건너뜀)

1. https://search.google.com/search-console → 속성 추가 → `teameet.co.kr`
2. 사이트맵 제출: `sitemap.xml`
3. **URL 검사** 도구로 `/teams`·`/matches` 를 넣어 "페이지 가져오기" → 렌더된 HTML 에
   목록이 보이는지 확인 (이번 작업의 효과를 구글 쪽에서 직접 확인하는 방법입니다)

## 7. 읽는 법 — 숫자가 움직이면 무슨 뜻인가

- **노출이 먼저, 클릭은 나중**: 구조를 고치면 **노출(검색 결과에 뜬 횟수)**부터 움직입니다.
  클릭은 제목·설명이 매력적이어야 따라와요. 노출만 늘고 클릭이 안 늘면 다음 작업은 **메타 문구**입니다.
- **주말에 떨어지는 건 정상**: 평일에 몰리는 주제는 주말 노출이 꺼집니다. 오히려 실제 수요라는 증거예요.
- **검색어 목록이 다음 할 일**: 서치어드바이저·GSC 의 상위 검색어 중 **전용 페이지가 없는 질문**이
  다음에 만들 페이지입니다.
- **크롤러 방문이 먼저, 인용은 나중**: 5-2 의 숫자가 0에서 벗어나야 5-3 의 인용을 기대할 수 있습니다.

## 8. 함정 — 측정하다 틀리기 쉬운 곳

- **배포 직후 측정 금지**: 서버 캐시(ISR)가 배포 직후엔 **빌드 시점의 빈 값**을 한 번 돌려줍니다.
  실제로 2026-09-01 에 이걸로 "기능이 안 된다"고 오진할 뻔했습니다(sitemap 8개 → 12초 뒤 494개).
  응답 헤더 `x-nextjs-cache` 가 `STALE` 이면 그 요청이 갱신을 시작한 것이니, **한 번 더 쳐서** 재세요.
- **낡은 데이터는 모든 검사를 통과합니다**: "0이 아님"만 보는 확인은 며칠 전 값이 계속 내려와도
  통과시킵니다. 값이 아니라 **값의 날짜**를 함께 보세요.
- **브라우저로 본 것은 증거가 아닙니다**: 브라우저는 자바스크립트를 실행하므로 잘 보입니다.
  판정은 항상 `curl` 로 받은 HTML 기준입니다.
