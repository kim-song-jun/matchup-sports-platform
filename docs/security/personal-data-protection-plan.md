# 팀밋 개인정보 저장 보호 수준과 단계별 적용 계획

작성: 2026-11-19 · 상태: 전체 구현 진행 중, 별도 모듈/비밀번호 개선 및 진행 게이트 기록 · 기준: origin/dev `fb9e768aa`

실제 적용 여부와 차단 조건: [구현 현황](./personal-data-implementation-status.md). 서비스 개인정보 저장 암호화는 아직 적용되지 않았다.

작업 추적: [Task 20261137](../../.github/tasks/20261137-personal-data-protection-plan.md).
이 문서는 현재 구현 증거, 외부 권장 기준, 팀밋의 제안을 구분한다. 문서 작성은 암호화 적용·운영 검증·법적 적합성 판정을 의미하지 않는다. 최초 산출물은 계획 문서였다. 후속 코드의 실제 적용 범위와 미완료 항목은 구현 현황 문서를 따른다. 운영 DB·키·설정을 변경한 것은 아니다.

## 1. 결정 요약

팀밋에는 **저장장치·백업 보호 + 주요 개인정보 필드 암호화 + 관리자 원문 열람 통제**를 목표로 권장한다. 비밀번호는 복원 가능한 암호화 대신 적정 비용의 단방향 해시를 사용한다. 공개 닉네임·팀명·경기 점수까지 일괄 암호화하는 범위는 제안하지 않는다.

먼저 확인할 것은 실제 디스크/백업 암호화, 저장 위치, 조회 주체, 개인정보 복사본이다. 그다음 이메일·전화번호·실명·생년월일과 인증 자격 증명을 보호한다. 데이터 최소 수집·보유기간·삭제·복구 절차까지 함께 다뤄야 한다.

이메일·전화번호 암호화는 로그인, 계정 연결, 중복 검사와 검색에 영향을 준다. 어드민 개선 PR #2447과 분리해 구현하고, 검색 UX를 확정한 다음 스키마를 설계한다. 해당 PR의 포함 기능을 현재 dev에 배포된 기능으로 가정하지 않는다.

## 2. 보통 어느 정도까지 하는가

아래는 업계 도입률에 관한 통계가 아니라, 공개 보안 가이드를 서비스 위험도에 맞춰 정리한 **이 문서의 비교 구분**이다. 특정 인증 등급이나 모든 업체가 실제로 구현한 수준을 의미하지 않는다.

| 구분 | 보호 범위 | 팀밋 판단 |
|---|---|---|
| 기본 보호 | 비밀번호 해시, TLS, 접근 제한, 최소 수집, 디스크·백업 암호화, 시크릿 분리, 로그 마스킹, 삭제/복구 절차 | 우선 실측하고 부족한 부분부터 보완 |
| 개인정보를 다루는 서비스의 강화 목표 | 기본 보호 + 연락처/비공개 식별정보 필드 암호화, 키 수명 관리, 관리자 마스킹·열람 감사, 복사본 통제 | 팀밋 권장 목표 |
| 위험도가 높은 업무의 추가 통제 | 목적별 키·권한 분리, 강화 인증, 대량 반출 통제, 승인 절차, 지속 탐지와 독립 보안 검증 | 결제·신분증·의료 등 실제 취급 범위가 생길 때 별도 평가 |

OWASP는 위협에 따라 암호화를 적용할 계층을 선택하고, 저장할 민감정보 자체를 최소화하며, 인증된 암호화 모드를 사용할 것을 권고한다. 디스크 보호와 앱 필드 보호는 서로 다른 유출 경로를 다룬다. [Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)

### 법적 최소 기준과 제품 보안 목표의 구분

2026-07-01 시행 「개인정보의 안전성 확보조치 기준」 제7조는 비밀번호의 일방향 저장, 열거된 이용자 정보의 저장 암호화, 인터넷망 전송 암호화 등을 규정한다. 이 문서가 권장하는 이메일·전화번호·실명·생년월일 필드 암호화를 곧바로 그 조문의 일률적 의무 목록으로 설명하지 않는다. 적용 의무는 실제 처리 항목·업무·시스템 구성으로 판단해야 한다. 접속기록 보관·점검은 제8조의 적용 조건을 확인해 보유기간과 담당자를 확정한다. [국가법령정보센터 현행 기준 제7·8조](https://www.law.go.kr/LSW/admRulInfoR.do?admRulSeq=2100000281400)

## 3. 현재 상태: 코드로 확인한 것과 미확인 항목

코드 조사이며 실제 회원 레코드, `.env`, 운영 키, 운영 DB 덤프는 열람하지 않았다. 아래 목록은 초기 인벤토리이며 모든 개인정보 경로를 전수 검증한 결과가 아니다.

| 모델 / DB 테이블 | 확인한 저장 정보 | 코드 기준 현황 / 후속 |
|---|---|---|
| `V1User` / `v1_users` | email, phone | 일반 문자열 + unique. 가입 시 그대로 전달. 필드 암호화 필요 후보 |
| `V1UserProfile` / `v1_user_profiles` | realName, birthDate, nickname, bio, 이미지 URL | 일반 문자열. 비공개 원정보와 공개 표시 정보 구분 필요 |
| `V1AuthIdentity` / `v1_auth_identities` | email, providerUserKey, passwordHash, providerRefreshTokenCiphertext | 이메일/소셜 식별자도 복사본 범위. 비밀번호는 scrypt+랜덤 salt, Apple 갱신 토큰은 AES-256-GCM |
| `V1PhoneVerificationChallenge`, `V1EmailVerificationChallenge`, `V1VerificationToken`, `V1LoginStepUpChallenge` | 수신 대상, 코드/토큰 검증값 | codeHash/tokenHash 필드 존재. 이름만으로 충분한 보호를 인정하지 않고 생성 알고리즘·키·만료·시도 제한 점검 |
| `V1TournamentPlayer` / `v1_tournament_players` | realName, birthDateSnapshot, eligibilityNote | 회원 프로필 외 별도 원정보/스냅샷. 자격 판정·정렬·공개 표시 영향 조사 |
| `V1Inquiry` / `v1_inquiries` | guestEmail, guestPhone, 자유 입력 내용 | 비회원 연락처와 자유 입력·첨부까지 별도 보유/삭제 범위 |
| `V1AdminActionLog` / `v1_admin_action_logs` | reason, beforeJson, afterJson | 감사 JSON에 개인정보를 복사하는 경로 전수 점검 필요 |
| 프로필 외 경기·명단·내보내기·채팅·파일·캐시 | 표시 스냅샷/연락처가 포함될 가능성 | 목록 확정 전에는 보호 완료로 분류하지 않음 |

확인 근거:

- [Prisma schema](../../apps/v1_api/prisma/schema.prisma), [가입·로그인 저장 경로](../../apps/v1_api/src/auth/auth.service.ts).
- [비밀번호 해시](../../apps/v1_api/src/auth/password-hash.ts): scrypt 호출에 비용 옵션을 명시하지 않는다. 알고리즘 이름만으로 현재 권장 강도를 충족한다고 판정하지 않는다.
- [Apple token 암호화](../../apps/v1_api/src/auth/apple-token-cipher.ts): AES-256-GCM, 랜덤 IV, identity ID에 바인딩한 인증 데이터 사용. 개인정보용 키와 그대로 공유하지 않는다.
- [관리자 검색](../../apps/v1_api/src/admin/admin-user-filters.ts): 이메일/실명 contains, 전화번호 부분 검색을 사용한다. 일반 HMAC 일치 검색으로 그대로 대체할 수 없다.
- [현재 로그 설정](../../apps/v1_api/src/common/logging/pino-http.config.ts): 인증 헤더·쿠키 등의 redaction이 이미 있다. 모든 query/body/오류/감사 JSON의 개인정보 보호까지 확인된 것은 아니다.
- [계정 최종 삭제](../../apps/v1_api/src/users/final-account-deletion.ts): 프로필 실명·생년월일 삭제 처리가 이미 있다. 오래된 계획 문서의 “파기 미구현” 설명을 현행 사실로 재사용하지 않는다.
- [Prisma 서비스](../../apps/v1_api/src/prisma/prisma.service.ts), [배포 compose](../../deploy/docker-compose.prod.yml): 검토한 경로에서는 주요 개인정보의 자동 필드 암호화가 확인되지 않는다. 운영 디스크/EBS·스냅샷·외부 백업·DB 연결 TLS의 실제 상태는 미확인이다.

## 5. 설계 제안과 먼저 결정할 사항

### 5.1 암호화와 키 관리

- 검증된 구현으로 AES-256-GCM 등 인증된 암호화를 사용한다. 암호문에는 포맷 버전·키 식별자·IV·tag를 포함하고, 인증 데이터에 환경·모델·행 ID·필드 목적을 결합한다. 같은 키로 IV가 재사용되지 않게 한다.
- 개인정보 키, 검색 HMAC 키, 세션 서명 키, Apple token 키를 목적별로 분리한다. alpha/prod도 분리한다.
- AWS KMS 기반 envelope encryption을 우선 설계안으로 삼는다. DB에는 암호문/래핑된 키만 두고, 복호화 권한은 필요한 API·워커 역할로 제한한다. CI 빌드 역할에는 운영 복호화 권한을 주지 않는다.
- 키 ID로 구·신 버전 읽기를 지원하되 신규 쓰기는 최신 버전만 사용한다. 키 캐시의 수명·권한 회수 지연·KMS 장애 동작을 명시한다. 복호화 오류를 빈 값이나 평문 fallback으로 숨기지 않는다.
- 키 회전, 유출 시 회수, 백업 복원에 필요한 구 키 보존, 파기를 구분한다. 키 삭제로 정상 복구가 불가능해지지 않도록 승인된 보유정책과 연결한다.

키 저장소·접근 통제·전체 수명 관리를 별도 설계해야 한다는 근거: [OWASP Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html). 이 문서의 KMS 구성은 팀밋을 위한 제안이며 현재 적용 사실이 아니다.

### 5.2 검색·중복 검사·계정 연결

- 이메일은 현재 서비스의 대소문자/공백 정책을 먼저 고정한다. 검증 없이 공급자별 점·플러스 주소를 합치지 않는다. 전화번호는 지원 국가/형식과 함께 정규화한다.
- 정규화한 값에 목적 구분을 넣은 HMAC을 사용한다. 이메일/전화번호처럼 값 공간이 작은 정보에 키 없는 SHA-256만 적용해 보호 완료로 보지 않는다. HMAC도 동일값/빈도 정보를 드러내며 익명 데이터가 아니다.
- 로그인, 가입 중복 확인, 이메일 변경, 소셜/이메일 로그인 연결·해제, 비회원 인증, 탈퇴 후 재가입까지 동일한 유일성 계약을 유지한다. `providerUserKey`의 이메일 복사본도 포함한다.
- **기본 제안:** 개인정보는 전체 값 정확 일치 검색, 공개 닉네임/회원 ID는 기존 탐색 유지. 기존 개인정보 부분 검색을 조용히 없애지 않고 변경 사유와 대체 입력을 제공한다.
- 부분 검색이 필수라면 별도 승인할 검색 계약을 설계한다. 평문 보조 컬럼, 전체 회원 복호화 스캔, 이메일/전화번호 n-gram의 무분별한 색인을 기본 해법으로 사용하지 않는다. 후자는 조각·빈도 누출을 추가한다.
- 키 교체 중 검색 누락/중복 가입을 막는 이중 버전 조회·고유성 보호·재색인 절차를 구현한다. 해시 키 버전별 unique만 추가해서 논리적 중복이 생기지 않도록 동시성 테스트한다.

### 5.3 관리자·공개 응답

- 목록은 마스킹 값을 반환하고, 별도 서버 capability로 원문 열람을 통제한다. UI에서만 가리지 않는다.
- 원문 열람은 목적·최소 범위·대상·행위자·시간·성공/실패를 감사한다. 권한 회수·세션 만료·대량 열람 제한을 검증한다. 조회 전용 회원 접속이 개인정보 원문 열람 권한을 자동 부여하지 않는다.
- 대회 운영자의 자격 확인과 플랫폼 관리자 권한을 분리한다. 실명 공개 선택과 내부 원문 열람 권한도 별도다.
- 공개 API·SSR·웹 캐시·푸시·CSV·오류 응답에 연락처/생년월일이 포함되지 않는지 검증한다. 개인정보 응답의 캐시와 신원 전환 정리도 확인한다.

### 5.4 암호화의 보호 범위

| 유출 경로 | 주요 방어 | 남는 한계 |
|---|---|---|
| 디스크/스냅샷 유출 | 저장장치·백업 암호화 | 실행 중 DB의 정상 조회는 막지 못함 |
| SQL 조회 권한/DB 덤프만 유출 | 앱 필드 암호화 + 키 분리 | 공개값/검색 동일성은 남을 수 있음 |
| 앱 프로세스·복호화 권한 탈취 | 최소권한·키 감사·네트워크/계정 통제 | 필드 암호화만으로 방지 불가 |
| 관리자 계정 오용 | 역할 제한·마스킹·열람 감사·대량 반출 통제 | 정당한 열람 이후 촬영/복사 위험은 별도 |
| 로그·파일·백업 복사본 | 최소 저장·redaction·보유/복원 통제 | 주요 회원 테이블만 바꾸면 잔존 가능 |

## 6. 단계별 실행 계획

현재는 계획만 작성한다. 아래 산정은 API/웹/DB/인프라 작업을 한 명이 순차 수행할 때의 **초기 작업일 범위**로, 인벤토리·검색 선택·실측 결과에 따라 다시 산정한다. 운영 승인/대기·외부 법무/보안 검토와 배포 관찰 기간은 별도이며 완료일 약속이 아니다.

| 단계 | 내용과 산출물 | 선행/완료 게이트 | 초기 산정 |
|---|---|---|---|
| P0 현황 확정 | 모든 PII 원본·복사본·읽기/쓰기·보유기간 목록, 디스크/백업/TLS/권한 증거 | 미확인 항목 소유자 지정, 검색·보유 범위 결정 | 2–3일 |
| P1 노출 통제 | 기존 로그 보호 보완, 관리자 응답 최소화·마스킹·열람 계약 | API/ops/public 권한 및 누출 회귀, 설계 영향 API 문서화 | 2–4일 |
| P2 기반 | 암호문/키 버전, KMS 역할·회전·장애, HMAC 정규화, 비밀번호 비용 검증 | 위변조/오키/복사/교체 실패, 성능·동시성 증거 | 4–6일 |
| P3 계정 전환 | 회원/프로필/인증·계정 연결/인증 challenge, 추가 컬럼·인덱스·백필 도구 | 로그인·중복 검사·탈퇴·재가입·롤백 검증 | 5–8일 |
| P4 복사본 전환 | 대회 명단·문의·감사 JSON·파일·발송·내보내기·캐시 | P0 전체 목록 processed M/N, 원문 잔존과 권한 검증 | 5–8일 |
| P5 배포·복구 | Alpha 실측·복구 훈련·소규모 운영 전환·평문 제거 | 실패 0, 백필 불일치 0, 운영/백업 잔존 처리 승인 | 2–4일 |

첫 검토 가능한 구간은 P0+P1의 약 4–7작업일이며, 암호화 전체 전환은 합계 약 20–33 작업일(약 4–7주)을 초기 범위로 본다. P4 대상이 늘거나 부분 검색 유지가 필수이면 증가한다. P0→P2→P3→P4→P5의 공유 계약은 순차 처리한다. P1은 P0 이후 먼저 적용 가능하다. 현재 실행은 단일 세션이며 병렬 에이전트는 사용하지 않는다.

권장 PR 단위는 (1) 인벤토리·노출 통제, (2) 키/crypto·비밀번호 포맷, (3) 계정 expand와 이중 호환, (4) 백필·읽기 전환, (5) 도메인 복사본, (6) 평문 contract와 복구 런북이다. DB DDL과 데이터 백필은 기존 expand/contract·운영 승인 계약을 따른다. dev 검증 후 운영 승격은 사용자가 수행한다.

## 7. 데이터 전환·롤백 계획

1. **Expand:** 암호문/검색값/키 버전 nullable 컬럼·필요 인덱스를 추가한다. 구 컬럼 삭제 금지. 기존 배포와 스키마 호환성 검증.
2. **호환 배포:** 모든 API·워커 쓰기 경로를 포괄한 전환 버전을 배포한다. 기존 평문 유지가 필요한 과도기는 기간/담당자를 정하고, 이를 보호 완료로 표시하지 않는다. 원문 암호화 누락 쓰기를 검출한다.
3. **백필:** 승인된 대상에서 작은 cursor 배치로 실행한다. 재시작·중복 실행·부분 실패·동시 수정과 행 버전 충돌을 처리하고, 이미 바뀐 값을 이전 값으로 덮지 않는다. 로그에는 ID·개수·실패 코드만 남긴다. DB reset/seed로 대체하지 않는다.
4. **검증·읽기 전환:** 행별 성공 상태와 집계, 중복/정규화 충돌, 복호화 일치, 실제 로그인/연락처 변경/계정 연결을 확인한다. 암호문 존재 시 위변조/복호화 실패를 평문 fallback으로 숨기지 않는다. 아직 미전환인 행만 명시한 호환 규칙으로 처리한다.
5. **평문 쓰기 중단:** 모든 배포 인스턴스/워커/잡이 새 쓰기 계약을 사용하는지 확인한다. 검색·unique 계약 전환과 구 버전 롤백 가능 경계를 명시한다.
6. **Contract:** 승인된 관찰 기간·복구 검증 뒤 평문 컬럼/보조 색인과 불필요한 복사본을 제거한다. 최초부터 한 migration으로 데이터를 파괴하지 않는다.
7. **백업·복구:** 기존 백업의 평문은 새 DB 적용만으로 사라지지 않는다. 보존/만료·접근 통제·구 키를 문서화하고, 복원 시 삭제 요청 재적용과 재암호화 검증을 완료하기 전 서비스에 노출하지 않는다.

롤백은 평문 제거 전에는 호환 버전으로만 가능하며, 제거 후에는 암호문을 읽는 복구 버전을 사용한다. 구 키 상실은 단순 앱 롤백으로 복구되지 않는다. 장애 시 쓰기를 보류/명시 실패시키고 평문 저장으로 되돌리는 자동 fallback을 만들지 않는다.

## 8. 검증과 완료 기준

| 영역 | 필요한 실제 증거 |
|---|---|
| 암호 경계 | 동일 평문 반복 암호화 시 암호문 변화, 위변조/다른 행·필드/잘못된 키 거부, 키 버전 교체·환경 격리 |
| 계정 계약 | 가입·로그인·비밀번호 재설정·소셜 연결/해제·이메일/전화번호 변경·탈퇴/재가입, 동시 중복 가입 및 키 교체 중 고유성 |
| 관리자/운영 | 실제 HTTP에서 무권한 원문 거부, 기본 마스킹, 원문 열람 감사, 회원 대리접속으로 권한 확장 불가 |
| 데이터 전환 | 실제 격리 PostgreSQL에서 백필 중 재시작/실패/동시 수정/복구, 평문 제거 뒤 정상 조회·삭제 |
| 노출 검사 | DB dump 표본, 로그·감사 JSON·API·캐시·CSV·푸시·파일에서 합성 민감값 추적. 결과에는 실제 PII 미기재 |
| 성능/운영 | 로그인 비용·동시 부하, 검색 지연·실행 계획, KMS 지연/장애/쿼터, 키 회수·회전·백업 복구 |
| 사용자 흐름 | ego-lite로 Alpha 실제 로그인, 회원/관리자/대회 운영자 시나리오. 변경 화면은 390/768/1440 및 console/network 증거 |

완료는 단순 round-trip 단위 테스트나 UI 마스킹 확인만으로 선언하지 않는다. P0에서 확정한 전체 대상 M/N을 보고하고 예외는 사유·담당자·기한을 명시한다. 실패 계약은 가능하면 RED→GREEN으로 증명한다. 고부하 검증 전 호스트 상태를 확인하며, 변경 범위의 좁은 검증부터 최소 worker로 실행한다.

## 9. 결정 목록과 다음 행동

| 결정 | 권장 초안 | 확정 시점 |
|---|---|---|
| 개인정보 검색 | 전체 이메일/전화번호 정확 일치 + 공개 닉네임/회원 ID 탐색 | P0, 화면/API 변경 전 |
| 생년월일 | 종목·대회 자격 판정에 필요한 정밀도만 보관 | P0, 도메인 담당 확인 |
| 키 관리 | 환경·목적 분리한 KMS envelope 구성, 기존 Apple 키 재사용 금지 | P2 설계 전 |
| 원문 열람 역할 | 현재 owner/ops 역할을 그대로 전부 허용하지 않고 업무별 capability로 정의 | P1 구현 전 |
| 보유·삭제 | 원본/스냅샷/문의/감사/백업별 목적·기간·삭제 책임 명시 | P0 및 법적 적용 검토 |
| 비밀번호 | Argon2id와 명시적 scrypt 비용을 측정해 선택, 버전 해시·로그인 시 업그레이드 | P2 구현 전 |
| 부분 검색 유지 필요 | 기본안은 미지원 전환 제안, 필요하면 별도 누출/운영 비용 평가 | P0, 사용자 선택 필요 |

다음 구현의 첫 산출물은 **PII 인벤토리와 검색 계약 확정안**이다. 이 계획 자체를 승인된 스키마나 운영 데이터 변환 지시로 간주하지 않는다.
