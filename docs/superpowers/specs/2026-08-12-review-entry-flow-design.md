# 후기 진입 동선 통합 — 갈라진 3갈래를 하나의 흐름으로

작성일: 2026-08-12
관련 문서: [팀 후기 작성 권한 개방](./2026-08-12-team-review-open-to-all-participants-design.md)

## 현황 (기)

후기가 서로 다른 3갈래로 존재하고, 진입 동선이 제각각이다.

| 후기 종류 | 데이터 모델 | 현재 진입 동선 |
|---|---|---|
| 대회 **운영** 후기 | `V1TournamentReview` | 홈 화면 팝업 + 마이페이지 카드 |
| 대회 경기 **상대팀** 평가 | `V1PostEventReview` (tournament_fixture) | **없음** — `/my/reviews` 직접 방문 |
| 팀 매치 **상대팀** 평가 | `V1PostEventReview` (team_match) | 마이페이지 매치 목록의 "리뷰" 버튼 |

추가로 확인된 사실:

- **후기 독려 알림이 아예 없다.** `apps/v1_api/src/notifications/`에 review 언급 0건.
  반면 `apps/v1_web/src/lib/notification-route.ts:6`에는 알림을 `/my/reviews`로 보내는 라우팅
  규칙이 이미 있다 — 받는 쪽 준비는 끝났는데 보내는 쪽이 없는 상태다.
- 대회 운영 후기 팝업은 `sessionStorage`에 닫힘을 저장해서(`pending-review-modal.tsx:12,28`)
  세션이 바뀌면 다시 뜬다.

## 문제 (승)

같은 "후기"인데 사용자가 세 곳을 각각 찾아다녀야 하고, 그중 하나(대회 경기 상대팀 평가)는
사실상 입구가 없다.

이 문제는 진행 중인 [작성 권한 개방](./2026-08-12-team-review-open-to-all-participants-design.md)과
직결된다. 상대팀 평가 권한을 팀원 전원에게 열었지만, 그 후기에는 팝업도 알림도 없다.
팀장은 마이페이지 매치 목록에서 "리뷰" 버튼이라도 보지만, 일반 팀원은 자신이 후기를 쓸 수
있게 됐다는 사실 자체를 알 방법이 없다. **권한만 열고 문을 열지 않으면 개방 효과가 거의 나지
않는다.**

## 대안 검토 (전)

**각 진입점을 개별 보강** — 세 갈래를 그대로 두고 각각에 팝업·알림을 붙인다. 변경 범위는
작지만 사용자 입장에서는 한 대회가 끝난 뒤 팝업이 여러 번 뜨는 것처럼 느껴진다. 후기가 세
종류라는 건 내부 사정이지 사용자가 알 바가 아니다.

**백엔드까지 한 모델로 통합** — `V1TournamentReview`를 `V1PostEventReview`로 흡수한다.
개념적으로는 가장 깔끔하지만 두 모델의 유니크 제약·집계 경로·어드민 숨김 기능이 모두 달라
마이그레이션 비용이 크고, 진행 중인 권한 개방 작업과 같은 테이블에서 충돌한다.

→ **프론트 흐름만 묶는다.** 백엔드 API는 그대로 두고 화면에서 순차 호출한다.

## 설계 (결)

### 1. 통합 후기 흐름

대회 종료 시 진입점 하나에서 순서대로 묻는다.

```
[대회 종료]  → "OO컵 어떠셨나요?"
   1단계  대회 운영은 어땠나요?      → POST /tournaments/:id/reviews
   2단계  A팀과의 경기는 어땠나요?   → POST /reviews
   3단계  B팀과의 경기는 어땠나요?   → POST /reviews
          (조별예선 + 결선에서 만난 팀 수만큼 반복)
```

- 각 단계는 건너뛸 수 있다. 중간에 이탈해도 남은 항목은 배지에 남는다.
- 모델·권한 변경 없음. 두 API를 순차 호출할 뿐이다.
- 팀 매치는 상대팀이 하나뿐이므로 1단계짜리 같은 흐름을 쓴다.

### 2. 4채널 역할 분담

네 채널을 모두 쓰되 **발화 횟수를 채널마다 다르게** 둔다. 같은 후기를 네 번 재촉하지 않는
것이 이 설계의 핵심 제약이다.

| 채널 | 역할 | 발화 횟수 |
|---|---|---|
| 웹 푸시 + 인앱 알림 | 앱 밖에 있는 사람에게 도달 | 대회/경기 종료 시 **1회** |
| 홈 팝업 | 앱을 열었을 때 주목 | 대회당 **1회**, 닫으면 종료 |
| 마이페이지·하단바 배지 | 조용한 상시 리마인드 | 미작성이 남는 동안 상시 |

푸시와 인앱 알림은 기존 `createNotificationWithPrefCheck()`
(`apps/v1_api/src/notifications/notifications.service.ts:351`) **한 번 호출로 둘 다 처리**된다.
알림 선호도 확인과 푸시 실패 무시(fire-and-forget)가 이미 들어 있다. 새로 만들 것은 후기용
알림 타입과 선호도 필드 하나다.

### 3. 팝업 dismiss를 서버 기록으로

현재 `sessionStorage` 방식은 세션이 바뀌면 팝업이 다시 뜬다. 팝업만 있을 때는 문제가 아니었지만
푸시·배지가 함께 붙으면 과하게 느껴진다. dismiss 시각을 서버에 기록해 기기가 바뀌어도 다시
뜨지 않게 한다.

### 4. 트리거

| 대상 | 지점 |
|---|---|
| 대회 | 어드민의 `in_progress → completed` 전환 (`tournaments-admin.service.ts:36`) |
| 팀 매치 | 경기 완료 처리 지점 |

**발송 대상: 참가팀의 active 멤버 전원** (푸시 포함). 작성 권한과 범위를 일치시킨다 —
"쓸 수 있는 사람"과 "알림 받는 사람"이 다르면 그 자체가 새로운 혼란이 된다.

## 트레이드오프

| | 지금 | 변경 후 |
|---|---|---|
| 장점 | 알림이 없어 조용하다. 팝업 dismiss 구현이 단순(클라이언트 only) | 입구가 하나로 모여 발견 가능. 팀원 전원에게 실제로 도달. 후기 수집률 상승 |
| 단점 | 상대팀 평가는 사실상 발견 불가. 권한 개방 효과가 나지 않음 | **대회에 안 간 팀원도 푸시를 받는다.** dismiss 상태를 서버에 저장해야 해서 테이블·API가 늘고, 4채널 상태를 일관되게 유지할 책임이 생긴다 |

푸시를 참가팀 멤버 전원에게 보내는 선택의 대가는 명확하다 — 대회에 참가하지 않은 팀원도
핸드폰 알림을 받는다. 이를 완화하되 없애지는 못하는 장치로, 후기 알림 선호도 필드를 만들어
사용자가 이 종류만 끌 수 있게 한다. 기본값은 켜짐이다.

또 하나 남는 부담: 팝업·배지·알림의 "미작성" 판정이 세 곳에서 각각 계산되면 서로 어긋날 수
있다. 판정 로직은 단일 소스(pending 조회)에서만 나오게 하고 세 채널이 그 결과를 공유한다.

## 작업 순서

이 작업은 [권한 개방 작업](./2026-08-12-team-review-open-to-all-participants-design.md)이
머지된 뒤 시작한다 — 같은 후기 테이블을 건드리므로 동시에 진행하지 않는다.

1. 후기용 알림 타입 + 알림 선호도 필드 추가 (스키마 + 마이그레이션)
2. 대회 종료 / 팀 매치 완료 트리거에 알림 발송 훅
3. pending 판정 단일 소스 정리 (팝업·배지·목록이 같은 결과를 쓰도록)
4. 통합 후기 흐름 프론트 구현 (대회 운영 → 상대팀 N개 순차)
5. 팝업 dismiss 서버 기록 전환
6. 배지 노출 (마이페이지 + 하단바)
